### Блок 1. Отказ от циклов

**Код на Си** (строка 57):
```c
for(i = 0; i < 3; i++) ivector[i] = 1;
```

**Неоптимизированный код (`-O0`)** — настоящий цикл со счётчиком, сравнением и переходами:
```asm
    mov   DWORD PTR i[rip], 0      ; i = 0
    jmp   .L2
.L3:
    mov   eax, DWORD PTR i[rip]    ; взять i
    cdqe
    lea   rdx, 0[0+rax*4]          ; адрес ivector[i]
    lea   rax, ivector[rip]
    mov   DWORD PTR [rdx+rax], 1   ; ivector[i] = 1
    mov   eax, DWORD PTR i[rip]
    add   eax, 1                   ; i++
    mov   DWORD PTR i[rip], eax
.L2:
    cmp   eax, 2                   ; i < 3 ?
    jle   .L3                      ; да → повторить
```

**Оптимизированный код (`-O2`)** — цикл убран, три прямые записи:
```asm
    mov   rax, QWORD PTR .LC0[rip]     ; .LC0 = две упакованные единицы {1, 1}
    mov   DWORD PTR ivector[rip+8], 1  ; ivector[2] = 1
    mov   QWORD PTR ivector[rip], rax  ; ivector[0] и ivector[1] = 1,1 одной командой
```

**Комментарий:** компилятор определил, что цикл всего лишь записывает 1 в три соседние
ячейки, и полностью **развернул его**, убрав счётчик, сравнение и переходы. Две соседние
ячейки `int` (8 байт) записаны одной 64-битной командой через заранее подготовленную
в памяти константу `.LC0`. Вместо ~15 команд с ветвлением — 3 линейные команды.

### Блок 2. Переприсваивание (удаление мёртвых присваиваний)

**Код на Си** (строки 62–64):
```c
i2 = 5;
j4 = 6;
i2 = j4;
```

**Неоптимизированный код (`-O0`)** — выполняется всё дословно:
```asm
    mov   DWORD PTR i2[rip], 5     ; i2 = 5
    mov   DWORD PTR j4[rip], 6     ; j4 = 6
    mov   eax, DWORD PTR j4[rip]   ; взять j4
    mov   DWORD PTR i2[rip], eax   ; i2 = j4
```

**Оптимизированный код (`-O2`)** — всё схлопнулось в одну команду:
```asm
    mov   DWORD PTR i2[rip], 6     ; i2 = 6
```

**Комментарий:** `i2 = 5` сразу перезаписывается следующим `i2 = j4`, поэтому это
**мёртвое присваивание** — компилятор его убрал. Значение `j4 = 6` известно на этапе
компиляции (константа), и дальше `j4` переопределяется до использования, поэтому вместо
`i2 = j4` подставлено `i2 = 6` (размножение констант), а отдельная запись `j4 = 6` удалена
как ненужная. Три присваивания превратились в одно.

> Важно: при `-O2` команды **переставлены** и не идут в порядке исходника. Чтобы найти блок,
> ищи по переменной (например, где `i2` получает значение), а не по порядку строк.

### Блок 3. Размножение констант и копий

**Код на Си** (строки 69–79):
```c
j4 = 2;
if( i2 < j4 && i4 < j4 ){ i2 = 2; printf("Hello"); }
j4 = k5;
if( i2 < j4 && i4 < j4 ){ i5 = 3; printf("Hello"); }
```

**Неоптимизированный код (`-O0`)** — каждое сравнение перезагружает `i2` и `j4` из памяти:
```asm
    mov   DWORD PTR j4[rip], 2      ; j4 = 2
    mov   edx, DWORD PTR i2[rip]    ; загрузить i2
    mov   eax, DWORD PTR j4[rip]    ; загрузить j4
    cmp   edx, eax                  ; i2 < j4 ?
    jge   .L4
    mov   edx, DWORD PTR i4[rip]    ; загрузить i4
    mov   eax, DWORD PTR j4[rip]    ; снова загрузить j4
    cmp   edx, eax                  ; i4 < j4 ?
    jge   .L4
    mov   DWORD PTR i2[rip], 2      ; i2 = 2
    ...                             ; printf; дальше второй if — так же, с перезагрузками
```

**Оптимизированный код (`-O2`)**:
```asm
    ; ПЕРВОГО if нет вообще: i2=6, j4=2 → 6 < 2 всегда ложно
    mov   eax, DWORD PTR k5[rip]    ; j4 = k5
    cmp   eax, 6                    ; i2 < j4  →  6 < k5   (i2=6 подставлено константой!)
    mov   DWORD PTR j4[rip], eax
    jle   .L6
    cmp   eax, DWORD PTR i4[rip]    ; i4 < j4  →  i4 < k5
    jg    .L16                      ; .L16: i5 = 3; printf
.L6:
```

**Комментарий:** компилятор знает, что `i2 = 6` (из блока 2), поэтому вместо загрузки `i2`
из памяти **подставил константу 6** прямо в сравнение (`cmp eax, 6`) — размножение константы.
Первый `if` вычислен на этапе компиляции: `6 < 2` всегда ложно → весь блок с `i2=2` и `printf`
удалён. Второй `if` остался (значение `k5` неизвестно), но без лишних перезагрузок из памяти.

### Блок 4. Свёртка констант, арифметические тождества, лишние load/store

**Код на Си** (строки 86–92):
```c
i3 = 1 + 2;          // свёртка констант
flt_1 = 2.4 + 6.3;   // свёртка констант (вещественная)
i2 = 5;
j2 = i + 0;          // тождество: + 0
k2 = i / 1;          // тождество: / 1
i4 = i * 1;          // тождество: * 1
i5 = i * 0;          // тождество: * 0
```

**Неоптимизированный код (`-O0`)** — тождества уже упрощены:
```asm
    mov   DWORD PTR i3[rip], 3            ; 1 + 2  →  посчитано в 3
    movsd xmm0, QWORD PTR .LC1[rip]       ; 2.4 + 6.3  →  готовая константа 8.7
    movsd QWORD PTR flt_1[rip], xmm0
    mov   DWORD PTR i2[rip], 5
    mov   eax, DWORD PTR i[rip]           ; j2 = i   (+ 0 убрано)
    mov   DWORD PTR j2[rip], eax
    mov   eax, DWORD PTR i[rip]           ; k2 = i   (/ 1 убрано)
    mov   DWORD PTR k2[rip], eax
    mov   eax, DWORD PTR i[rip]           ; i4 = i   (* 1 убрано)
    mov   DWORD PTR i4[rip], eax
    mov   DWORD PTR i5[rip], 0            ; i5 = 0   (* 0)
```

**Оптимизированный код (`-O2`)** — те же свёртки, но константы идут дальше: `i5 = 0` и `i2 = 5`
позже подставляются в блок 9 (`k5 = i5 + i2` превращается в `k5 = 5` на этапе компиляции).

**Комментарий:** ⚠️ важный момент. Свёртка констант (`1+2 → 3`, `2.4+6.3 → 8.7`) и
арифметические тождества (`i+0 → i`, `i/1 → i`, `i*1 → i`, `i*0 → 0`) настолько базовые, что GCC
делает их **даже на `-O0`** — поэтому в «неоптимизированном» столбце они уже упрощены, разницы
по этим строкам между `-O0` и `-O2` почти нет. Разница `-O2` в другом: полученные константы
распространяются по программе и схлопывают последующие блоки.

### Блок 5. Лишнее присваивание

**Код на Си** (строки 114–115):
```c
k3 = 1;
k3 = 1;
```

**Неоптимизированный код (`-O0`)**:
```asm
    mov   DWORD PTR k3[rip], 1     ; k3 = 1
    mov   DWORD PTR k3[rip], 1     ; k3 = 1  (повтор)
```

### Блок 6. Снижение мощности

**Код на Си** (строки 121–123):
```c
k2 = 4 * j5;
for( i = 0; i <= 5; i++ )
    ivector4[i] = i * 2;
```

**Неоптимизированный код (`-O0`)**:
```asm
    mov   eax, DWORD PTR j5[rip]
    sal   eax, 2                   ; 4 * j5  →  сдвиг влево на 2 (вместо умножения)
    mov   DWORD PTR k2[rip], eax
    ...                            ; цикл: i*2 считается сложением (lea [rax+rax])
```

**Оптимизированный код (`-O2`)**:
```asm
    mov   eax, DWORD PTR j5[rip]
    sal   eax, 2                   ; 4 * j5  →  тот же сдвиг
    mov   DWORD PTR k2[rip], eax
    ...
    mov   DWORD PTR ivector4[rip+8], 655368  ; цикл развёрнут и посчитан:
    mov   QWORD PTR ivector4[rip], rax       ; значения 0,2,4,6,8,10 записаны константами
```

**Комментарий:** снижение мощности — замена дорогой операции дешёвой: `4 * j5` компилятор
делает **сдвигом** `sal eax, 2` (быстрее умножения) уже на `-O0`, `i*2` — сложением.
На `-O2` цикл дополнительно развёрнут, а значения `i*2` посчитаны заранее и записаны двумя
широкими командами.

### Блок 7. Простой цикл

**Код на Си** (строки 129–135):
```c
j5 = 0;  k5 = 10000;
do {
    k5 = k5 - 1;
    j5 = j5 + 1;
    i5 = (k5 * 3) / (j5 * 5);
} while ( k5 > 0 );
```

**Неоптимизированный код (`-O0`)** — полный цикл, выполняется 10000 раз (`sub`, `add`,
умножения, `idiv` на каждой итерации).

**Оптимизированный код (`-O2`)**:
```asm
    mov   DWORD PTR i5[rip], 0        ; i5 = 0      (итог последней итерации)
    mov   DWORD PTR j5[rip], 10000    ; j5 = 10000  (0 + 10000 инкрементов)
    ; самого цикла НЕТ — ни sub, ни idiv
```

**Комментарий:** компилятор проанализировал цикл и **посчитал его результат на этапе
компиляции**: за 10000 проходов `j5` досчитывается до 10000, итоговый `i5 = 0` (в последнем
проходе деление `0*3 / …` даёт 0). Цикл из 10000 итераций исчез полностью — осталось два
присваивания.

### Блок 8. Управление переменной индукции цикла

**Код на Си** (строки 140–141):
```c
for( i = 0; i < 100; i++ )
    ivector5[ i*2 + 3 ] = 5;
```

**Неоптимизированный код (`-O0`)** — каждый проход считает индекс `i*2+3`, из него адрес, пишет 5.

**Оптимизированный код (`-O2`)**:
```asm
    lea   rax, ivector5[rip+12]   ; указатель на ivector5[3]  (3*4 = 12 байт)
    lea   rdx, 800[rax]           ; граница конца
.L7:
    mov   DWORD PTR [rax], 5      ; *p = 5
    add   rax, 16                 ; p += 16  (шаг = 2 элемента, цикл развёрнут ×2)
    mov   DWORD PTR -8[rax], 5    ; соседний элемент
    cmp   rdx, rax
    jne   .L7
```

**Комментарий:** вместо пересчёта индекса `i*2+3` и адреса на каждом проходе (умножение +
сложение) компилятор завёл **указатель**, который просто шагает по памяти на фиксированные
16 байт. Переменная индукции `i` заменена прямым движением по массиву — умножение из цикла
ушло. Это тот самый цикл, на который `-O2` выдал предупреждение о выходе за границу `ivector5`
(индекс `i*2+3` убегает за 100 ячеек) — то есть предупреждение и есть побочный результат
этого анализа.

### Блок 9. Глубокие подвыражения

**Код на Си** (строки 147–150):
```c
if( i < 10 )
    j5 = i5 + i2;
else
    k5 = i5 + i2;
```

**Неоптимизированный код (`-O0`)** — загрузить `i`, сравнить с 9, ветвление; в ветке загрузить
`i5`, `i2`, сложить, записать.

**Оптимизированный код (`-O2`)**:
```asm
    mov   DWORD PTR i[rip], 100    ; i уже известно = 100 (итог цикла блока 8)
    mov   DWORD PTR k5[rip], 5     ; i>=10 → ветка else: k5 = i5 + i2 = 0 + 5 = 5
```

**Комментарий:** к этому месту компилятор знает `i = 100`, `i5 = 0`, `i2 = 5`. Условие
`i < 10` ложно → берётся `else`, а подвыражение `i5 + i2` посчитано как `5`. Весь `if/else`
схлопнулся в одну запись `k5 = 5`.

### Блок 10. Константный адрес, копии и регистры

**Код на Си** (строки 158–161):
```c
ivector[0]  = 1;
ivector[i2] = 2;
ivector[i2] = 2;
ivector[2]  = 3;
```

**Неоптимизированный код (`-O0`)**:
```asm
    mov   DWORD PTR ivector[rip], 1     ; ivector[0] — прямой адрес
    mov   eax, DWORD PTR i2[rip]        ; загрузить i2
    ...                                 ; ivector[i2] = 2  (lea адреса, запись)
    mov   eax, DWORD PTR i2[rip]        ; СНОВА загрузить i2
    ...                                 ; ivector[i2] = 2  (повтор)
    mov   DWORD PTR ivector[rip+8], 3   ; ivector[2] — прямой адрес (смещение 8)
```

**Оптимизированный код (`-O2`)**:
```asm
    mov   DWORD PTR ivector[rip], 1     ; ivector[0] = 1
    mov   DWORD PTR ivector[rip+20], 2  ; ivector[i2] = 2  (i2=5 → смещение 20), ОДИН раз
    mov   DWORD PTR ivector[rip+8], 3   ; ivector[2] = 3
```

**Комментарий:** для `ivector[0]` и `ivector[2]` адрес — константа (прямое смещение) уже на
`-O0`. На `-O2`: индекс `i2` известен (=5), поэтому `ivector[i2]` стал прямым смещением `+20`
без загрузки `i2` и подсчёта адреса; два одинаковых `ivector[i2]=2` подряд схлопнуты в одну
запись.

### Блок 11. Удаление общих подвыражений (CSE)

**Код на Си** (строки 168–172):
```c
if(( h3 + k3 ) < 0 || ( h3 + k3 ) > 5 )
    printf("Common subexpression elimination\n");
else {
    m3 = ( h3 + k3 ) / i3;
    g3 = i3 + ( h3 + k3 );
}
```

**Неоптимизированный код (`-O0`)** — `h3 + k3` считается заново все четыре раза (загрузить `h3`,
загрузить `k3`, сложить — ×4).

**Оптимизированный код (`-O2`)**:
```asm
    mov   ecx, DWORD PTR h3[rip]   ; h3 загружено ОДИН раз
    lea   edx, 1[rcx]              ; h3 + k3  (k3=1) посчитано ОДИН раз → переиспользуется
    cmp   edx, 5
    ja    .L17                     ; «< 0 или > 5» одним беззнаковым сравнением
    ...                            ; m3 = (h3+k3)/i3 и g3 = i3+(h3+k3) берут готовое edx
    add   ecx, 4                   ; g3 = 3 + (h3+1) = h3 + 4
```

**Комментарий:** общее подвыражение `h3 + k3` встречается четыре раза; `-O2` посчитал его
**один раз** (как `h3 + 1`, зная `k3 = 1`) и переиспользовал — удаление общих подвыражений.
Попутно подставлено `i3 = 3`, а проверка «меньше 0 или больше 5» сжата в одно беззнаковое
сравнение.

### Блок 12. Вынесение инвариантного кода из цикла

**Код на Си** (строки 180–183):
```c
for( i4 = 0; i4 <= 2; i4++){
    printf("Hello");
    ivector2[i4] = j * k;
}
```

**Неоптимизированный код (`-O0`)** — цикл, каждую итерацию считает `j * k` (загрузить `j`, `k`, `imul`).

**Оптимизированный код (`-O2`)**:
```asm
.L10:
    lea   rcx, .LC1[rip]           ; "Hello"
    call  printf
    movzx eax, BYTE PTR k[rip]     ; k снова загружается ВНУТРИ цикла
    mul   BYTE PTR j[rip]          ; j * k считается КАЖДУЮ итерацию
    mov   BYTE PTR [rbx+r8], al    ; ivector2[i4] = результат
    ...  cmp/jle .L10
```

**Комментарий:** ⚠️ методичка ждёт, что `j * k` (не зависит от `i4`) будет **вынесено** из
цикла. Но `-O2` этого **не сделал**: `j` и `k` — глобальные переменные, а в цикле есть вызов
`printf`. Компилятор не может доказать, что вызов не меняет глобальные `j`/`k`, поэтому на
всякий случай пересчитывает `j*k` каждую итерацию. Вывод: вынесение инварианта срабатывает
только когда компилятор уверен в неизменности значения (были бы `j`, `k` локальными или не было
бы вызова — вынес бы).

---

### Блок 13. Мёртвый код (функция `dead_code`)

**Код на Си** (строки 211–220):
```c
void dead_code( int a, char *b ){
    int idead_store;
    idead_store = a;
    if( 0 ) printf( "%s\n", b );
}
```

**Неоптимизированный код (`-O0`)**:
```asm
dead_code:
    ...
    mov   eax, DWORD PTR 16[rbp]   ; idead_store = a
    mov   DWORD PTR -4[rbp], eax
    nop                            ; if(0) — тело не сгенерировано, но запись осталась
    ret
```

**Оптимизированный код (`-O2`)**:
```asm
dead_code:
    ret                            ; тело пустое
```
Вдобавок в `main` **вызова `dead_code` нет вообще**.

**Комментарий:** `idead_store = a` — запись в локальную переменную, которую никто не читает
(мёртвая запись); `if(0)` — недостижимый код. На `-O2` тело функции пусто, а сам вызов из
`main` удалён — функция ничего наблюдаемого не делает.

---

### Блок 14. Ненужный цикл (функция `unnecessary_loop`)

**Код на Си** (строки 230–238):
```c
void unnecessary_loop(){
    int x;  x = 0;
    for( i = 0; i < 5; i++ )
        k5 = x + j5;
}
```

**Неоптимизированный код (`-O0`)** — цикл крутится 5 раз, каждый раз `k5 = x + j5`.

**Оптимизированный код (`-O2`)**:
```asm
unnecessary_loop:
    mov   eax, DWORD PTR j5[rip]   ; j5
    mov   DWORD PTR i[rip], 5      ; i = 5       (итоговое значение счётчика)
    mov   DWORD PTR k5[rip], eax   ; k5 = j5     (x=0 → k5 = 0 + j5)
    ret
```

**Комментарий:** тело цикла не зависит от счётчика — каждый проход делает одно и то же.
Компилятор убрал цикл и оставил только итог: `i = 5`, `k5 = j5`. Вызов из `main` сохранён —
функция меняет глобальные переменные.

---

### Блок 15. Слияние циклов (`loop_jamming`)

**Код на Си** (строки 247–254):
```c
void loop_jamming( int x ){
    for( i = 0; i < 5; i++ ) k5 = x + j5 * i;
    for( i = 0; i < 5; i++ ) i5 = x * k5 * i;
}
```

**Неоптимизированный код (`-O0`)** — два отдельных цикла по 5 итераций.

**Оптимизированный код (`-O2`)**:
```asm
loop_jamming:
    mov   eax, DWORD PTR j5[rip]
    mov   DWORD PTR i[rip], 5          ; i = 5
    lea   eax, [rcx+rax*4]             ; k5 = x + j5*4  (только последняя итерация, i=4)
    mov   DWORD PTR k5[rip], eax
    imul  eax, ecx                     ; i5 = k5 * x ...
    sal   eax, 2                       ;        * 4     (i=4)
    mov   DWORD PTR i5[rip], eax
    ret
```

**Комментарий:** ⚠️ методичка ждёт **слияния** двух циклов (одинаковый заголовок) в один.
GCC сделал больше: `k5` и `i5` глобальные, на каждой итерации перезаписываются — важен только
итог последней итерации (`i = 4`). Поэтому оба цикла **удалены целиком**, оставлены финальные
значения: `k5 = x + j5*4`, `i5 = x*k5*4`.

---

### Блок 16. Разворот цикла (`loop_unrolling`)

**Код на Си** (строки 265–270):
```c
void loop_unrolling( int x ){
    for( i = 0; i < 6; i++ )
        ivector4[i] = 0;
}
```

**Неоптимизированный код (`-O0`)** — цикл 6 итераций, каждая пишет 0 в `ivector4[i]`.

**Оптимизированный код (`-O2`)**:
```asm
loop_unrolling:
    mov   QWORD PTR ivector4[rip], 0      ; ivector4[0..3] = 0 (8 байт одной командой)
    mov   DWORD PTR ivector4[rip+8], 0    ; ivector4[4..5] = 0 (ещё 4 байта)
    mov   DWORD PTR i[rip], 6             ; i = 6
    ret
```
В `main` этот код ещё и **встроен** (inlined) вместо `call loop_unrolling`.

**Комментарий:** цикл обнуления 6 ячеек (`short`, 12 байт) развёрнут и слит в две широкие
записи (8 + 4 байта), счётчик `i = 6` выставлен сразу. В `main` функция вдобавок встроена
по месту вызова.

---

### Блок 17. Сжатие цепочки переходов (`jump_compression`)

**Код на Си** (строки 279–300, суть):
```c
... else { j += k; end_1: goto beg_1; } ...
// переход goto end_1, а end_1 сам содержит goto beg_1 — цепочка из двух прыжков
```

**Неоптимизированный код (`-O0`)** — есть метка `end_1` (`.L40 → nop`), отдельная `.L38` с
`jmp .L32` (на `beg_1`). Переход идёт в два шага: сначала на `end_1`, оттуда на `beg_1`.

**Оптимизированный код (`-O2`)** — промежуточная метка `end_1` убрана, переход ведёт **сразу**
на `beg_1`:
```asm
    cmp   r9d, r10d      ; if( l < m )
    jl    .L27           ; да → l += m, return
    cmp   edx, ecx       ; иначе СРАЗУ назад на проверку i<j (beg_1), без захода на end_1
    jle   .L21
.L20:                    ; beg_1
    ...
```
В `main` вызов `jump_compression(1,2,3,4,5)` **удалён** — результат не используется, побочных
эффектов нет.

**Комментарий:** сжатие цепочки переходов — `goto end_1`, где `end_1` сам содержит `goto beg_1`,
превращается в **один прямой переход** на `beg_1`; лишний прыжок через промежуточную метку убран.
Вызов из `main` удалён целиком.

---

## 3-Os. Третий столбец: что делает `-Os` по каждому блоку

Сравниваем всё с `-O0`. Выше разобрано `-O0 → -O2`; здесь по тем же 17 блокам — `-O0 → -Os`.
Итог: **по 11 блокам `-Os` делает ровно то же, что `-O2`** (те же удаления, свёртки, подстановки),
отличается только в 6 блоках — и каждое отличие показывает компромисс «скорость против размера».

**Обзор по всем блокам:**

| Блок | `-Os` относительно `-O2` |
|------|--------------------------|
| 1. Отказ от циклов | то же (цикл убран), но константу `{1,1}` вшивает прямо в команду `movabs`, не читает из памяти |
| 2. Переприсваивание | идентично (`i2 = 6`) |
| 3. Размножение констант | идентично (первый `if` удалён, `cmp eax, 6`) |
| 4. Свёртка / тождества | идентично |
| 5. Лишнее присваивание | идентично (одна запись `k3`) |
| 6. Снижение мощности | то же, но массив `ivector4` заполняет через `movabs`, не из памяти |
| 7. Простой цикл | идентично (цикл удалён: `j5 = 10000`, `i5 = 0`) |
| **8. Переменная индукции** | **ОТЛИЧИЕ:** `-Os` цикл **не разворачивает** (1 запись за проход), `-O2` разворачивает ×2 |
| 9. Глубокие подвыражения | идентично (`k5 = 5`) |
| 10. Константный адрес | идентично |
| **11. Общие подвыражения** | CSE то же, но деление на 3 делает **настоящей `idiv`**, а `-O2` — умножением на «магическое» число |
| 12. Вынесение инварианта | идентично (`j*k` НЕ вынесено) |
| 13. Мёртвый код | идентично (тело пусто, вызов удалён) |
| 14. Ненужный цикл | идентично (3 команды, вызов сохранён) |
| 15. Слияние циклов | идентично (оба цикла удалены) |
| **16. Разворот цикла** | **ОТЛИЧИЕ:** `-O2` **встраивает** `loop_unrolling` в `main`, `-Os` оставляет `call` |
| **17. Сжатие переходов** | **ОТЛИЧИЕ:** `-O2` **удаляет вызов** из `main`, `-Os` его **сохраняет** |

Ниже — фрагменты `-Os` для блоков, где есть отличие.

### Блок 1 (`-Os`) — константа в команде, а не в памяти

```asm
    movabs rax, 4294967297           ; 0x1_0000_0001 = две единицы в одном 64-битном числе
    mov    DWORD PTR ivector[rip+8], 1
    mov    QWORD PTR ivector[rip], rax
```
`-O0 → -Os`: цикл так же развёрнут и убран. Отличие от `-O2`: `-O2` читал готовую пару `{1,1}`
из памяти (`mov rax, .LC0[rip]`), `-Os` вшил её прямо в команду `movabs` — так короче по числу
байт данных.

### Блок 6 (`-Os`) — то же, упакованные значения через `movabs`

```asm
    movabs rax, 1688867040264192     ; упакованные short 0,2,4,6
    mov    QWORD PTR ivector4[rip], rax
    mov    DWORD PTR ivector4[rip+8], 655368   ; 8,10
```
Эффект тот же, что у `-O2` (цикл развёрнут в константы), разница только в способе получить
константу (команда вместо чтения из памяти).

### Блок 8 (`-Os`) — цикл НЕ развёрнут

```asm
    lea   rcx, ivector5[rip+4]
    xor   eax, eax
.L15:
    inc   rax
    cmp   rax, 101
    je    .L25
    mov   DWORD PTR [rcx+rax*8], 5   ; ОДНА запись за проход (шаг *2 зашит в масштаб *8)
    jmp   .L15
```
`-O0 → -Os`: индекс `i*2+3` тоже заменён движением по памяти (переменная индукции), но цикл
**оставлен цельным** — один `mov` за итерацию, 100 проходов. Отличие от `-O2`: тот разворачивал
цикл по 2 элемента за проход (длиннее, но быстрее). Это главный пример «размер против скорости».

### Блок 11 (`-Os`) — настоящее деление вместо умножения

```asm
    lea   eax, 1[rcx]     ; h3 + k3 посчитано ОДИН раз (CSE — как в -O2)
    cmp   eax, 5
    jbe   .L18
    ...
    mov   r8d, 3
    idiv  r8d            ; m3 = (h3+k3) / 3  — НАСТОЯЩАЯ команда деления
    add   ecx, 4         ; g3 = h3 + 4
```
Удаление общего подвыражения — как у `-O2`. Отличие: деление на 3 `-O2` заменяет умножением на
«магическое» число (быстрее, но длиннее), а `-Os` оставляет короткую команду `idiv` (короче,
но медленнее).

### Блок 16 (`-Os`) — функция НЕ встроена

```asm
loop_unrolling:
    xor   eax, eax
    xor   edx, edx
    mov   DWORD PTR i[rip], 6
    mov   QWORD PTR ivector4[rip], rax    ; = 0
    mov   DWORD PTR ivector4[rip+8], edx  ; = 0
    ret
```
В `main` — `call loop_unrolling`. Тело оптимизировано как у `-O2` (цикл развёрнут в 2 записи),
но `-O2` **встраивает** эту функцию прямо в `main` (нет вызова), а `-Os` оставляет вызов:
встраивание дублирует код и растит размер, поэтому `-Os` его избегает.

### Блок 17 (`-Os`) — вызов сохранён

Тело `jump_compression` сжато так же, как у `-O2` (переход сразу на `beg_1`). Но в `main`
`-Os` **сохраняет** `call jump_compression`, тогда как `-O2` удаляет этот вызов целиком.
Причина: `-O2` делает больше межпроцедурного анализа — доказывает, что функция без побочных
эффектов и её результат не используется, → убирает вызов; `-Os` такой вызов оставляет.

**Вывод по `-Os` против `-O2`:** базовые оптимизации (свёртки, удаление мёртвого кода и циклов,
CSE, подстановка констант) у них одинаковы. Различия — ровно там, где `-O2` ради скорости
**увеличивает** код: разворот цикла (блок 8), умножение вместо деления (блок 11), встраивание
функции (блок 16), удаление пустого вызова через тяжёлый анализ (блок 17). `-Os` все эти
«разгоны» не делает — отсюда и меньший размер (868 против 1028 байт).

## 4. Оптимизация по размеру (`-Os`)

Файл скомпилирован в объектный (`.o` — машинный код только нашего кода, без рантайма)
с тремя режимами, размеры секций получены утилитой `size`:

```
C:\mingw64\bin\gcc -O0 -c OPTBENCH.c -o optbench_O0.o
C:\mingw64\bin\gcc -O2 -c OPTBENCH.c -o optbench_O2.o
C:\mingw64\bin\gcc -Os -c OPTBENCH.c -o optbench_Os.o
C:\mingw64\bin\size optbench_O0.o optbench_O2.o optbench_Os.o
```

`[СКРИН 3: вывод size по трём .o]`
Подпись: *Рисунок 3 — сравнение размеров секций при разных уровнях оптимизации.*

**Размер секции `.text` (код):**

| Сборка | `.text`, байт | Доля от `-O0` |
|--------|--------------:|--------------:|
| `-O0` (без оптимизаций) | 1780 | 100 % |
| `-O2` (по скорости) | 1028 | 58 % |
| `-Os` (по размеру) | **868** | 49 % |

(`data` = 0, `bss` = 576 байт одинаково у всех — это глобальные массивы, от уровня оптимизации
не зависят.)

**Вывод по размеру.** Любая оптимизация сильно ужимает код относительно `-O0` (там каждая
строка Си переведена дословно). `-Os` — самый компактный: 868 байт, на ~16 % меньше `-O2`
и меньше половины от `-O0`. Экономия `-Os` идёт за счёт отказа от «ускоряющих, но
раздувающих» приёмов `-O2`.

**Вывод о читаемости листинга `-Os`.** Листинг `-Os` короче, но читается по-разному:
- `-O2` ради скорости **разворачивает** циклы и дублирует команды (цикл блока 8 идёт по
  2 элемента за проход, широкие записи) — листинг длиннее и дальше от исходника;
- `-Os` разворачивать избегает: тот же цикл блока 8 остаётся **простым циклом по одному
  элементу** — по структуре ближе к исходному коду и короче.

При этом оба оптимизированных листинга (и `-O2`, и `-Os`) читать **труднее**, чем `-O0`:
компилятор переставляет, сливает и удаляет команды, подставляет константы — код перестаёт
построчно соответствовать исходнику. `-O0` самый читаемый (прямая калька с Си), но самый
объёмный; `-Os` — компромисс: компактно и без разворотов, но с подстановкой констант и
удалением блоков.

## Выводы

В ходе работы изучены принципы работы оптимизирующего компилятора на примере `OPTBENCH.c`,
скомпилированного компилятором GCC 15.2.0 без оптимизаций (`-O0`), с оптимизацией по скорости
(`-O2`) и по размеру (`-Os`). Сравнение ассемблерных листингов показало конкретные
преобразования по 17 блокам: развёртывание и полное удаление циклов, свёртку констант и
арифметические тождества, размножение констант и копий, снижение мощности (замена умножения
сдвигом), удаление мёртвого кода и лишних присваиваний, удаление общих подвыражений, замену
переменной индукции цикла движением указателя, сжатие цепочек переходов, встраивание функций.

Отдельно отмечены три случая, важные для понимания границ оптимизации:
1. базовые упрощения (свёртка констант, тождества `i+0`, `i*1`, `i*0`) выполняются **даже на
   `-O0`** — это не «оптимизация по запросу», а всегда;
2. вынесение инварианта `j*k` из цикла **не произошло**, потому что `j`, `k` глобальные, а в
   цикле есть вызов `printf`: компилятор не может доказать неизменность значений;
3. два цикла в `loop_jamming` не просто слиты, а **удалены целиком** — компилятор посчитал,
   что наблюдаем только итог последней итерации.

По размеру кода: `-O2` — 58 %, `-Os` — 49 % от `-O0`. `-Os` даёт самый компактный код за счёт
отказа от разворота циклов; листинг `-Os` короче, но, как и `-O2`, менее читаем, чем `-O0`,
из-за переупорядочивания и удаления команд.
