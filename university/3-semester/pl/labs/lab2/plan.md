# План — Лабораторная работа №2. Числовые ребусы

**Цель.** Написать функцию, которая по строке‑ребусу находит любое валидное присвоение
цифр, затем оптимизировать её и замерить ускорение «до/после».
**Язык:** Go 1.24.0 (`/d/GO/bin/go`). В папке уже заведён `main.go`.
**Сквозная тема курса — оптимизация.** Здесь она прямо в задании.

---

## Что требует методичка (дословно по пунктам)

Функция: вход — строка‑ребус, выход — строка с валидным выражением.

Правила задачи:
- все буквы в верхнем регистре;
- одна буква ↔ одна цифра (разные буквы ↔ разные цифры);
- ведущие нули запрещены;
- действие только «+»;
- слагаемых в левой части — от 2 до 7 включительно;
- на вход подают только ребусы, у которых есть хотя бы одно решение (можно не проверять «нерешаемость»).

Порядок выполнения (4 пункта):
1. Создать репозиторий на GitHub.
2. Реализовать функцию.
3. Оптимизировать: **машинно‑независимые** оптимизации, **алгоритмические**, **эвристики**.
   Каждая оптимизация — **отдельный коммит**.
4. Сравнить скорость до/после, отразить в отчёте.

**Вывод для нас:** главный «артефакт» пункта 3 — это история git (видно, что менялось),
а пункта 4 — таблица времён. Три категории оптимизаций из методички задают структуру отчёта.

## Пункт 2. Разбор входа + базовая версия (V0)

### 2.1. Парсинг строки
Строку `"SEND + MORE = MONEY"` разбираем так:
- split по `"="` → левая часть и правая (результат);
- левую split по `"+"` → слагаемые;
- убрать пробелы (`strings.TrimSpace`);
- `words = слагаемые + [результат]`;
- собрать множество разных букв;
- запомнить **ведущие буквы** (первый символ каждого слова) — им нельзя быть нулём.

### 2.2. Математическая модель — веса букв (coefficient)
Каждое слово — это число: цифра · 10^(позиция справа). Весь ребус
`слагаемые = результат` сворачивается в одно уравнение по буквам:

```
для каждой буквы: вес = Σ (±10^позиция)   (+ у слагаемых, − у результата)
решение ⇔  Σ (вес_буквы · цифра_буквы) == 0,  все цифры разные,  ведущие ≠ 0
```

Это та же «школьная» арифметика в столбик, свёрнутая в формулу. На ней строятся все
быстрые версии. Но для V0 намеренно сделаем «в лоб», чтобы было что ускорять.

### 2.3. V0 — наивный полный перебор (baseline)
- хранить присвоение в `map[rune]int`;
- перебрать **все перестановки** цифр по буквам (выбор L разных цифр из 10);
- в проверке каждый раз **заново собирать** каждое слово в число из букв через map,
  сложить слагаемые, сравнить с результатом;
- пропускать варианты с ведущим нулём;
- первое совпадение → собрать строку ответа и вернуть.

Это «сделать, чтобы работало». Нарочно неэффективно (map + пересборка чисел каждый раз).

**Коммит:** `ЛР2: V0 — наивное решение (полный перебор)`.

## Пункт 3. Оптимизации (каждая — отдельный коммит)

Рекомендуемый формат: каждую версию держать **отдельной функцией** (`solveV0`, `solveV1`, …)
в своём файле. Тогда финальный бенчмарк сравнивает их все разом, а каждый коммит добавляет
одну версию. Альтернатива — эволюционировать одну функцию и мерить на каждом коммите
(чище diff, но мерить сложнее). Берём первый вариант.

### V1 — машинно‑независимые оптимизации (тот же алгоритм, дешевле константа)
Классика из теории компиляторов (перекликается с ЛР‑1):
- **вынос инварианта (loop‑invariant):** веса букв посчитать один раз заранее, в проверке
  больше не пересобирать числа из строк — только `Σ вес·цифра`;
- **map → массив** `[26]int` с индексом `буква-'A'` — убираем хеширование;
- только целочисленная арифметика, минимум аллокаций в горячем цикле.
Перебор перестановок остаётся тем же — ускоряется сама проверка.

**Коммит:** `ЛР2: V1 — машинно-независимые (веса заранее, массив вместо map)`.

### V2 — алгоритмическая: поиск с возвратом + отсечение (backtracking + pruning)
- не перебирать все перестановки; раздавать цифры буква за буквой в глубину (DFS);
- на каждом шаге проверять: занята ли цифра; не нарушен ли ведущий ноль;
- **отсечение:** если по уже розданным буквам частичная сумма `Σ вес·цифра` при самых
  оптимистичных остатках уже не может дать 0 — обрубить ветку.

**Коммит:** `ЛР2: V2 — backtracking с отсечением`.

### V3 — алгоритмическая: счёт по столбикам с переносами (опционально, самое сильное)
- решать по разрядам справа налево, протягивая перенос (carry), как мы считали руками
  `BE+BE=MOO`; на каждом столбце сразу проверять согласованность.
- Самое плотное отсечение, но заметно сложнее в коде. Делаем, если останется время.

**Коммит:** `ЛР2: V3 — столбики с переносами`.

### V4 — эвристики (heuristics)
- раздавать сначала буквы с наибольшим `|вес|` — тупиковые ветки отмирают раньше (fail fast);
- ранний выход на первом найденном решении (методичке хватает любого).

**Коммит:** `ЛР2: V4 — эвристика порядка перебора`.

**На что смотреть по ходу:** каждая версия на одних и тех же входах даёт **корректный** ответ
(сверка с проверкой суммы), и каждая следующая не медленнее предыдущей.

## Пункт 4. Замер скорости

### Набор тестов (от простого к тяжёлому)
- `BE + BE = MOO` — 4 буквы (мгновенно во всех версиях);
- `SEND + MORE = MONEY` — 8 букв (средний);
- `ELEVEN + NINE + FIVE + FIVE = THIRTY` — 10 букв, 4 слагаемых (тяжёлый: V0 = 10! перестановок).

10 букв = 3 628 800 перестановок — на нём и будет виден разрыв между V0 и оптимизациями.

### Как мерить — штатный бенчмарк Go
Файл `solve_test.go`, функции `BenchmarkV0`, `BenchmarkV1`, … (или табличный бенч по версиям×входам).

```bash
go test -bench=. -benchmem                 # ns/op и аллокации на операцию
go test -bench=BenchmarkV0 -benchtime=1x   # тяжёлый вход гонять 1 раз, иначе долго
```

- `-bench=.` — запустить все бенчмарки; `-benchmem` — показать память/аллокации;
- `-benchtime=1x` — ровно один прогон (для медленного V0 на 10 буквах).

Плюс маленький `main`, который печатает время через `time.Now()` — удобно для скриншота в отчёт.

### Корректность
`solve_test.go` с обычными тестами (`func TestSolve`): для каждого входа проверить, что
возвращённое выражение — настоящее равенство (левая сумма = правая) и правила соблюдены.
```bash
go test ./...                              # прогнать тесты
```

**На что смотреть:** таблица `версия | что изменили | ns/op | аллокаций | ускорение ×`.
Ускорение считать относительно V0.
