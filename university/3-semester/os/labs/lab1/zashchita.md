## 📌 0. Ответ за 30 секунд (если спросят «что вы сделали»)

В Pintos функция `timer_sleep()` усыпляла поток через **активное ожидание** — поток крутился в цикле и постоянно занимал процессор, ничего не делая. Мы это переделали: теперь поток вычисляет **тик, на котором его надо разбудить**, кладётся в **отсортированный список спящих** и **блокируется** (`thread_block`), полностью освобождая процессор. Обработчик прерываний таймера на каждом тике **будит** (`thread_unblock`) те потоки, у которых время пришло. Логику усыпления/пробуждения мы вынесли в `thread.c` (функции `thread_sleep`/`thread_awake`), а `timer.c` их вызывает. Результат: все 5 тестов `alarm-*` проходят, а процессор во время сна потоков простаивает (появились `idle ticks`).

## 1. Окружение и что такое Pintos

- **Pintos** — учебная ОС (Стэнфорд), работает на архитектуре **x86** внутри эмулятора **QEMU** (эмулятор — программа, которая изображает целый компьютер). Написана на C.
- **Почему через QEMU:** Pintos — полноценная ОС, ей нужно управлять «железом» напрямую; QEMU даёт ей виртуальную машину, которую она захватывает. Плюс безопасно и удобно (не рушит реальный ПК).
- Курс из 4 проектов; мы — в проекте **`threads`** (потоки, планировщик, таймер).
- **Рабочий цикл:** правим исходники в `~/pintos/src/…` → в каталоге `~/pintos/src/threads` собираем `make` → гоняем тесты в `build/`.

## 2. Краткая теория (то, что нужно помнить)

**Поток (thread) = процесс** в Pintos. Вся информация о нём — в `struct thread` (`threads/thread.h`). Процессор один, потоков много, **планировщик** переключает их.

**Состояния потока:**
| Состояние | Смысл |
|---|---|
| `RUNNING` | исполняется сейчас (ровно один) |
| `READY` | готов, ждёт очереди в `ready_list` |
| `BLOCKED` | заблокирован; планировщик его **не выбирает**, пока не разбудят |
| `DYING` | завершается |

**Тик (tick):** аппаратный таймер (микросхема **PIT 8254**) прерывает процессор **`TIMER_FREQ` = 100 раз в секунду**. Каждое прерывание = 1 тик (10 мс). Обработчик `timer_interrupt()` увеличивает глобальный счётчик `ticks` и вызывает `thread_tick()`.

**Прерывание** — сигнал процессору «брось всё, обработай событие». Прерывания нужны, чтобы **отбирать** процессор у потоков (без них поток `while(1){}` завис бы навсегда) и чтобы реагировать на устройства. Пока работает обработчик прерывания, прерывания **выключены**.

**Вытеснение (preemption):** `thread_tick()` считает, сколько тиков подряд работает поток; после `TIME_SLICE` = 4 тиков ставится флаг «уступи процессор». Так один поток не может держать процессор вечно.

**Ключевые различия:**
- `thread_yield()` — уступить процессор, но **остаться `READY`** (сразу обратно в очередь). Это и есть основа старого busy-wait.
- `thread_block()` — стать `BLOCKED` и **уйти из очереди** до явного пробуждения. Это то, что нам нужно.

## 3. Что было: проблема активного ожидания

Исходная `timer_sleep()`:

```c
void timer_sleep (int64_t ticks)
{
  int64_t start = timer_ticks ();
  ASSERT (intr_get_level () == INTR_ON);
  while (timer_elapsed (start) < ticks)   // пока не прошло нужное время
    thread_yield ();                       // уступить, но тут же вернуться в READY
}
```

**Как это работает:** `start` — снимок времени на входе. `timer_elapsed(start)` = `timer_ticks() - start` = сколько тиков прошло **с момента входа в функцию**. Пока прошло меньше, чем заказано (`ticks`), поток вызывает `thread_yield()` — уступает процессор, но остаётся `READY` и планировщик тут же выбирает его снова.

**Почему это плохо (активное ожидание / busy-wait):** поток не спит по-настоящему, он **постоянно занимает процессор** пустыми проверками «уже пора?». Процессорное время тратится впустую. Доказательство: тест `alarm-single` показывал `0 idle ticks` — процессор ни разу не простаивал, хотя все «спали». При планировании с приоритетами это может привести к тупику.

## 4. Что мы сделали: идея нового алгоритма

1. При `timer_sleep(N)` считаем **абсолютный тик пробуждения**: `wake_at = timer_ticks() + N`.
2. Сохраняем его в потоке, кладём поток в **отсортированный по `wake_at`** список спящих `sleep_list`.
3. **Блокируем** поток (`thread_block`) — он уходит из `ready_list`, процессор на него не тратится.
4. На каждом тике обработчик `timer_interrupt` вызывает `thread_awake`, который **будит** (`thread_unblock`) всех, у кого `wake_at <= ticks`.

Логику вынесли в `thread.c` (`thread_sleep`, `thread_awake`), потому что это операции над состояниями потоков; `timer.c` только считает `wake_at` и вызывает их.

**Изменения в 3 файлах:** `threads/thread.h`, `threads/thread.c`, `devices/timer.c`. Файл `timer.h` не трогали.

## 5. ВЕСЬ НАШ КОД С РАЗБОРОМ

### 5.1. `threads/thread.h` — два новых поля в `struct thread`

```c
int64_t wake_at;                /* Тик, на котором нужно разбудить поток. */
struct list_elem sleep_elem;    /* Крючок для включения потока в sleep_list. */
```

- **`wake_at`** — абсолютный номер тика (от загрузки ОС), на котором поток надо разбудить. `int64_t` — как и счётчик `ticks`, чтобы типы совпадали при сравнении.
- **`sleep_elem`** — «крючок» (узел двусвязного списка), которым поток вешается в `sleep_list`.

**Почему отдельный крючок, а не существующий `elem`?** У потока уже есть `elem` (для `ready_list` и списков семафоров) и `allelem` (для списка всех потоков `all_list`). Один `list_elem` физически может находиться **только в одном списке одновременно** (у него два указателя `prev`/`next`). Чтобы поток мог быть в `sleep_list` **и** в `all_list` одновременно, нужен третий, отдельный крючок.

Плюс два прототипа функций:
```c
void thread_sleep (int64_t wake_at);
void thread_awake (int64_t now);
```

### 5.2. `threads/thread.c`

**Список спящих потоков** (рядом с `ready_list`/`all_list`):
```c
static struct list sleep_list;
```
`static` = переменная видна **только внутри `thread.c`** (защита от доступа из других файлов).

**Инициализация** в `thread_init()`:
```c
list_init (&sleep_list);
```
`thread_init()` выполняется очень рано при загрузке — до того как хоть один поток попытается заснуть, так что список гарантированно готов. Передаём `&sleep_list` (адрес), потому что `list_init` меняет структуру через указатель.

**Функция сравнения** (компаратор для сортировки):
```c
static bool
sleep_earlier (const struct list_elem *a, const struct list_elem *b, void *aux UNUSED)
{
  return list_entry (a, struct thread, sleep_elem)->wake_at
       < list_entry (b, struct thread, sleep_elem)->wake_at;
}
```
- Тип этой функции — `list_less_func` (его требует `list_insert_ordered`).
- `list_entry(a, struct thread, sleep_elem)` — из крючка `a` восстанавливает **весь** `struct thread` (по смещению поля).
- Возвращает `true`, если поток `a` просыпается раньше `b` → список держится **по возрастанию `wake_at`**, в начале — тот, кому просыпаться раньше всех.
- `aux` не нужен → `UNUSED` (глушит предупреждение компилятора о неиспользуемом аргументе). `aux` — это «вспомогательные данные», общий механизм передать доп. контекст в колбэк; к процессам отношения не имеет.

**Усыпление:**
```c
void
thread_sleep (int64_t wake_at)
{
  struct thread *cur = thread_current ();
  enum intr_level old = intr_disable ();

  cur->wake_at = wake_at;
  list_insert_ordered (&sleep_list, &cur->sleep_elem, sleep_earlier, NULL);
  thread_block ();

  intr_set_level (old);
}
```
Построчно:
1. `cur = thread_current()` — текущий (усыпляемый) поток.
2. `old = intr_disable()` — **выключаем прерывания**, запоминаем прежний уровень.
3. `cur->wake_at = wake_at` — сохраняем момент пробуждения.
4. `list_insert_ordered(...)` — вставляем поток в `sleep_list` на нужное место (сортировка через `sleep_earlier`).
5. `thread_block()` — поток становится `BLOCKED` и отдаёт процессор. **Возврат из этой строки произойдёт позже**, когда поток разбудят.
6. `intr_set_level(old)` — вернуть прерывания как было (выполнится уже после пробуждения).

**Пробуждение:**
```c
void
thread_awake (int64_t now)
{
  struct list_elem *e = list_begin (&sleep_list);
  while (e != list_end (&sleep_list))
    {
      struct thread *t = list_entry (e, struct thread, sleep_elem);
      if (t->wake_at > now)      // ещё рано — а список отсортирован, значит и дальше рано
        break;
      e = list_remove (e);       // удалить из списка и получить следующий элемент
      thread_unblock (t);        // разбудить: BLOCKED -> READY
    }
}
```
Построчно:
1. `e = list_begin(&sleep_list)` — начинаем с начала списка (там ближайшее пробуждение).
2. Цикл, пока не дошли до конца (`list_end` — это «за-последний» маркер, сам не элемент).
3. `t = list_entry(e, …, sleep_elem)` — достаём поток из текущего крючка.
4. `if (t->wake_at > now) break;` — если этому потоку ещё рано просыпаться, то всем следующим (они позже) тоже рано → выходим из цикла.
5. `e = list_remove(e)` — снимаем поток из `sleep_list`; `list_remove` возвращает **следующий** элемент, поэтому обход продолжается корректно.
6. `thread_unblock(t)` — будим поток.

### 5.3. `devices/timer.c`

**Тонкая `timer_sleep`:**
```c
void
timer_sleep (int64_t ticks)
{
  ASSERT (intr_get_level () == INTR_ON);
  if (ticks <= 0)
    return;
  thread_sleep (timer_ticks () + ticks);   // абсолютный тик пробуждения
}
```
- `ASSERT(... == INTR_ON)` — функцию можно звать только при включённых прерываниях (иначе время замрёт и будить будет некому).
- `if (ticks <= 0) return;` — при 0 и отрицательном сне выходим сразу (тесты `alarm-zero`, `alarm-negative`). Раньше это делал сам цикл, теперь проверяем явно.
- `thread_sleep(timer_ticks() + ticks)` — считаем `wake_at` = сейчас + сколько спать, и делегируем в `thread.c`.

**Обработчик прерываний:**
```c
static void
timer_interrupt (struct intr_frame *args UNUSED)
{
  ticks++;
  thread_tick ();
  thread_awake (ticks);
}
```
- `ticks++` — увеличиваем общий счётчик тиков (это делает **сам** `timer_interrupt`).
- `thread_tick()` — статистика (`idle`/`kernel`/`user` тики) + вытеснение. **`ticks` она не трогает.**
- `thread_awake(ticks)` — наш вызов: разбудить всех, кому пора, на этом тике.

## 6. API-функции и макросы, которые мы используем

| Имя | Откуда | Что делает |
|---|---|---|
| `thread_current()` | thread.h | указатель на текущий (исполняющийся) поток |
| `thread_block()` | thread.h | текущий поток → `BLOCKED`, отдаёт процессор. **Требует выключенных прерываний**, нельзя из обработчика |
| `thread_unblock(t)` | thread.h | поток `t` → `READY`, кладёт в `ready_list`. **Можно** из обработчика прерывания |
| `timer_ticks()` | timer.h | число тиков с загрузки ОС (атомарное чтение) |
| `timer_elapsed(then)` | timer.h | `timer_ticks() - then` |
| `list_insert_ordered(&l,&e,less,aux)` | list.h | вставка с сохранением сортировки (нужен компаратор `less`) |
| `list_entry(e, тип, поле)` | list.h | по крючку `e` восстановить структуру `тип` (макрос, по смещению поля) |
| `list_begin/list_end/list_next` | list.h | обход списка (`list_end` — маркер конца, не элемент) |
| `list_front` | list.h | посмотреть первый элемент, не удаляя |
| `list_pop_front` | list.h | снять и вернуть первый элемент |
| `list_remove(e)` | list.h | удалить элемент, вернуть следующий |
| `list_empty(&l)` | list.h | пуст ли список |
| `intr_disable()` | interrupt.h | выключить прерывания, вернуть прежний уровень |
| `intr_set_level(old)` | interrupt.h | восстановить уровень прерываний |
| `intr_get_level()` | interrupt.h | текущий уровень (`INTR_ON`/`INTR_OFF`) |
| `ASSERT(x)` | debug.h | если `x` ложно — kernel panic (защитная проверка) |
| `UNUSED` | debug.h | пометка «аргумент не используется», глушит предупреждение |

## 7. Ключевые «ПОЧЕМУ» (для защиты)

**Почему `thread_block`, а не `thread_yield`?**
`yield` оставляет поток `READY` → он крутится в очереди и жжёт процессор (это и было busy-wait). `block` делает поток `BLOCKED` → он уходит из очереди, процессор на него не тратится.

**Почему список отсортирован?**
Чтобы обработчик таймера был **быстрым**. Обработчик срабатывает 100 раз в секунду. При сортировке ему достаточно посмотреть **начало** списка: если самому раннему ещё рано — всем рано, сразу выходим (`break`). Без сортировки пришлось бы проходить **весь** список каждый тик — это O(n) 100 раз в секунду. Мы сознательно сделали вставку дороже (O(n)), а горячий путь (обработчик) — дешёвым.

**Почему в `thread_sleep` выключаем прерывания?**
Три причины: (1) `sleep_list` использует ещё и обработчик таймера — если тик влезет посреди вставки, список порвётся (гонка данных); (2) `thread_block()` **требует** выключенных прерываний; (3) защита от «потерянного пробуждения» — чтобы не вышло, что поток уже в списке, но ещё не заблокирован, а его в этот момент пытаются разбудить.

**Почему в обработчике только `thread_unblock`, а не `thread_block`?**
Обработчик — это **не поток**, а особый режим (interrupt context). Заблокировать («усыпить») можно только настоящий поток; «усыпить прерывание» невозможно — его некуда отложить и вернуть. Поэтому в `timer_interrupt` разрешён только быстрый `thread_unblock`. (В `thread_block` даже стоит `ASSERT(!intr_context())`.)

**Почему `if (ticks <= 0) return;`?**
Раньше нулевое/отрицательное время отсекал сам цикл (условие сразу ложно). Цикла больше нет, поэтому проверяем явно — иначе тесты `alarm-zero` и `alarm-negative` сломались бы (или поток бы завис/уснул некорректно).

**Почему `wake_at` абсолютный (сейчас + N), а не «осталось N тиков»?**
С абсолютным значением обработчику на каждом тике достаточно **одного сравнения** `wake_at <= ticks`, ничего не пересчитывая. Если бы хранили «осталось», пришлось бы каждый тик у **всех** спящих уменьшать счётчик — дороже и сложнее.

**Почему вынесли в `thread.c`?**
Усыпление/пробуждение — это операции над **состояниями потоков** и над их очередью, логично держать их в `thread.c` (там же `thread_block`/`thread_unblock`/`ready_list`). `timer.c` остаётся тонким: считает `wake_at` и вызывает. Плюс это отличает наше решение от «всё в timer.c».

**Сложность:** вставка в `timer_sleep` — O(n) (поиск места в сортированном списке); проверка в обработчике — O(1) на «пустых» тиках + O(k) на k разбуженных.

## 8. Вероятные вопросы преподавателя + короткие ответы

**Q: Что такое активное ожидание и чем плохо?**
A: Поток в цикле постоянно проверяет условие, занимая процессор без пользы. Тратит процессорное время, при приоритетах может дать тупик.

**Q: Как теперь усыпляется поток?**
A: Считаем `wake_at`, кладём в отсортированный `sleep_list`, вызываем `thread_block` → поток `BLOCKED`, процессор свободен.

**Q: Кто и когда его будит?**
A: Обработчик таймера `timer_interrupt` на каждом тике вызывает `thread_awake`, который `thread_unblock`-ает всех, у кого `wake_at <= ticks`. Планировщик сам **не** будит.

**Q: Зачем поле `wake_at`?**
A: Чтобы обработчик знал, на каком тике будить поток. Без него разбудить было бы нечем.

**Q: Зачем отдельный `sleep_elem`, почему не `elem`?**
A: Один `list_elem` может быть только в одном списке. Поток должен быть в `sleep_list` и `all_list` одновременно → нужен отдельный крючок.

**Q: Зачем сортировать список?**
A: Чтобы обработчик работал быстро — проверяет только голову списка и делает `break`, если рано. Иначе O(n) каждый тик.

**Q: Зачем выключаете прерывания в `thread_sleep`?**
A: Защита `sleep_list` от гонки с обработчиком, требование `thread_block`, и защита от потерянного пробуждения.

**Q: Почему в обработчике нельзя `thread_block`?**
A: Обработчик — не поток, его нельзя заблокировать; можно только быстро разбудить других (`thread_unblock`).

**Q: Что делает `list_entry`?**
A: По адресу крючка (`list_elem`) вычисляет адрес всей структуры, в которую этот крючок встроен. Так из элемента списка получаем сам поток.

**Q: Разница `thread_block` и `thread_yield`?**
A: `yield` — остаться `READY` (вернуться в очередь); `block` — стать `BLOCKED` (уйти из очереди до пробуждения).

**Q: Что такое `idle ticks` и почему изменились?**
A: Тики, когда процессор простаивал (работал idle-поток). Было 0 (busy-wait жёг процессор), стало ненулевым — значит во время сна процессор реально свободен.

**Q: В каких файлах меняли?**
A: `threads/thread.h`, `threads/thread.c`, `devices/timer.c`. `timer.h` не трогали.

**Q: Что будет, если два потока должны проснуться на одном тике?**
A: Цикл `while` в `thread_awake` за один вызов снимет и разбудит всех подряд, у кого `wake_at <= now` (тест `alarm-simultaneous`).

**Q: Почему `int64_t`, а не `int`?**
A: Счётчик тиков `ticks` — 64-битный; чтобы типы `wake_at` и `ticks` совпадали и сравнение было корректным.

## 9. Доказательство тестами (до/после)

Пять тестов: `alarm-single`, `alarm-multiple`, `alarm-simultaneous`, `alarm-zero`, `alarm-negative` — все **pass**.

Показатель `idle ticks` (простой процессора):
| Тест | до | после |
|---|---|---|
| alarm-single | 0 | 250 |
| alarm-multiple | ~0 | 550 |
| alarm-simultaneous | ~0 | 250 |
| alarm-zero | 0 | 0 (сна нет) |
| alarm-negative | 0 | 0 (сна нет) |

Ненулевые `idle ticks` после = активное ожидание убрано, цель достигнута.

## 10. Глоссарий

- **Тик** — одно прерывание таймера, 1/100 сек.
- **Прерывание** — сигнал процессору «обработай событие».
- **Активное ожидание (busy-wait)** — цикл с постоянной проверкой условия, занимающий процессор.
- **`BLOCKED`/`READY`/`RUNNING`** — состояния потока.
- **Вытеснение** — принудительный отбор процессора у потока (после `TIME_SLICE`).
- **Крючок (`list_elem`)** — встроенный в структуру узел, которым её вешают в список.
- **idle-поток** — встроенный поток, работающий, когда нет готовых; его тики = `idle ticks`.
- **`TIMER_FREQ`** — 100, число прерываний таймера в секунду.
- **`static` (у глобальной)** — видимость только внутри своего `.c`-файла.
- **`ASSERT`** — проверка; если ложно — kernel panic.
