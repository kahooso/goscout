# Интерфейсы (interfaces)

## TL;DR
Интерфейс — контракт (набор сигнатур методов). Тип реализует его **неявно** (если имеет
все методы), без `implements`. Отделяет общий механизм от конкретной реализации.

## Где разобрано подробно
- `gobyexample.com/interfaces`
- `pkg.go.dev/io` (Reader/Writer — главные интерфейсы stdlib)
- `effective_go` → раздел Interfaces
- видео Николая Тузова: «Почему интерфейсы лучше размещать в месте использования» (15 мин)

## Минимальный пример
```go
type Probe interface {                              // контракт: список сигнатур без тел
    Run(ctx context.Context, target string) Result
    Name() string
}

type DNSProbe struct{}                              // реализация — структура (может быть пустой)
func (d DNSProbe) Name() string { return "dns" }    // value receiver
func (d DNSProbe) Run(ctx context.Context, target string) Result {
    addrs, err := net.DefaultResolver.LookupHost(ctx, target)
    return Result{Probe: "dns", Target: target, Output: addrs, Error: err}
}

var _ Probe = DNSProbe{}                            // compile-time страховка: реализует ли

probes := []Probe{ DNSProbe{}, PortProbe{} }        // слайс ИНТЕРФЕЙСОВ — полиморфно
for _, p := range probes { p.Run(ctx, target) }     // dynamic dispatch через itable
```

## Личный опыт

### Что я понял не сразу
- **ЗАЧЕМ интерфейс вообще** (главный затык task-08). Структуры `DNSProbe`/`PortProbe`
  пустые и «одинаковые» — казалось, бессмысленно. Суть: типы разные не ДАННЫМИ, а методом
  `Run` (РАЗНОЕ поведение — dns резолвит, ports сканирует). Интерфейс отделяет общий
  механизм (раннер с горутинами/каналом/select — ОДИН) от конкретной операции (проба).
  Новая проверка = новый тип + строка в switch, обвязку не трогаешь. Без интерфейса —
  копия многопоточной обвязки в каждой run-функции.
- **Аналогия (C/ядро):** `struct file_operations` в Linux — таблица указателей на функции
  (`read/write/open`). Ядро зовёт `file->ops->read()` единообразно, драйвер решает что это.
  Go-интерфейс = то же типобезопасно. В C это делают руками через struct указателей на функции.
- **Неявная реализация:** нет `implements`. Тип становится `Probe`, если имеет его методы.
  Проверка компилятором **в месте использования** (присваивание в интерфейс / передача в
  функцию), не глобальным сканом. Нет метода → ошибка с именем недостающего метода.
- **Пустая структура нормальна** — важны методы, не поля. Поля появятся, когда у реализации
  возникнут настройки (`PortProbe{ ports []int; timeout }`).

### На чём попадался (task-08)
- Пихал `ch chan Result` в сигнатуру `Run` (дважды) — Run НЕ знает про канал, возвращает
  Result; канал в раннере, горутина делает `ch <- p.Run(ctx,t)`. Лишний параметр ещё и ломает
  реализацию интерфейса (сигнатура не совпала).
- value vs pointer receiver: value receiver → и `T`, и `*T` реализуют; pointer receiver →
  ТОЛЬКО `*T`, голое значение `DNSProbe{}` в `[]Probe` не пройдёт (ошибка компиляции).
- `[]Probe` ≠ `[]*Probe` и ≠ `*Probe`. Это слайс интерфейс-ЗНАЧЕНИЙ. Указатель на данные уже
  ВНУТРИ интерфейс-значения → `[]*Probe` почти никогда не нужен. value/pointer определяется
  тем, что кладёшь в `[]Probe`, а не типом слайса.

### Подводные камни
- **Интерфейс в памяти = пара (itable-ptr, data-ptr).** itable — таблица адресов методов
  для пары (тип, интерфейс), как C++ vtable. Вызов = dynamic dispatch через неё.
- **nil-интерфейс:** вызов метода паникует. Интерфейс == nil только если ОБА указателя пусты.
- **typed-nil ловушка:** nil-указатель КОНКРЕТНОГО типа (`*MyErr`), возвращённый как
  интерфейс (`error`), делает интерфейс НЕ-nil (тип заполнен) → `err != nil` врёт.
  Лечится: возвращать литеральный `nil`, не заворачивать конкретный nil-указатель.
- Маленький интерфейс (1-2 метода, `io.Reader`) — идиома: чем меньше, тем больше типов
  подходят. «The bigger the interface, the weaker the abstraction.»

## Ключевые термины (English)
- `interface` — контракт из сигнатур методов
- `implicit implementation` — неявная реализация (без `implements`), structural typing
- `method set` — набор методов типа; решает, реализует ли он интерфейс
- `value` / `pointer receiver` — приёмник-значение / приёмник-указатель
- `dynamic dispatch` — выбор реализации метода в рантайме через таблицу
- `itable` / `vtable` — таблица адресов методов (как в C++)
- `duck typing` — «крякает как утка» (здесь — проверяемый компилятором)
- `typed nil` — nil-указатель конкретного типа в интерфейсе → интерфейс не nil
- `io.Reader` / `io.Writer` — ключевые однометодные интерфейсы stdlib
