# Горутины

## TL;DR

Лёгкая «зелёная нить» под управлением Go-рантайма (не ОС). `go f()` запускает `f`
параллельно и сразу возвращает управление. Тысячи горутин — норма.

## Где разобрано подробно

- `gobyexample.com/goroutines`, `gobyexample.com/waitgroups`
- `pkg.go.dev/sync` — `sync.WaitGroup`
- Видео Николая Тузова: «Анатомия Go: Как работает планировщик горутин на самом деле»
- Эффективное Go: раздел `effective_go.md#goroutines`

## Минимальный пример

```go
func runAll(tasks []string, fn func(string)) {
    var wg sync.WaitGroup
    for _, v := range tasks {
        wg.Add(1)              // ДО `go` — иначе гонка с Wait()
        go func(v string) {
            defer wg.Done()    // первой строкой — гарантия даже при панике fn
            fn(v)
        }(v)                   // v параметром — не закрытие на переменную цикла
    }
    wg.Wait()
}
```

## Личный опыт

### Что я понял не сразу

- **Горутина ≠ OS thread.** Думал что это `std::thread` из C++ — нет.
  В C++ thread это ~8 МБ стек, дорогое создание через syscall, ограничено ядрами.
  Горутина: 2 КБ растущего стека, дешёвое создание, M:N scheduling на N ОС-потоках.
  Большинство горутин ждут (I/O, таймер, канал) — пока одна ждёт, поток берёт другую.
- **`defer wg.Done()` ставить ПЕРВОЙ строкой, а не после `fn(v)`.** Если `fn` паникует
  до `defer` — defer вообще не зарегистрируется, счётчик не уменьшится → deadlock.
  Эту ошибку допустил в task-06.
- **Замыкание захватывает по ссылке.** Переменная цикла `v` — **одна** переменная,
  переиспользуется на каждой итерации. Если внутри горутины писать `fmt.Println(v)`
  без передачи параметром — все N горутин в конце увидят одно и то же `v` (последнее).
  Решение: `go func(v string){...}(v)` — копирует прямо в момент запуска.
- **`wg.Add(1)` строго ДО `go`.** Если внутри горутины — гонка: `wg.Wait()` может
  не успеть увидеть Add и вернуться раньше времени.
- **Main завершается → все горутины убиваются.** Без `wg.Wait()` ничего не успеет.

### На чём попадался

- task-06: `defer wg.Done()` поставил после `fn(v)` — мог сделать deadlock на панике
- task-06: пытался писать `go fn(v)` без wrapper-а — но тогда некуда поставить `defer wg.Done()`
- task-06: путал «передаю строку параметром, потому что строка — примитив»; настоящая
  причина — не «примитив/непримитив», а переиспользование переменной цикла

### Подводные камни

- `wg.Add(3)` + `Done()` только 2 раза → `wg.Wait()` блокируется навсегда (deadlock, рантайм паникует)
- `wg.Add(1)` внутри горутины → гонка с `wg.Wait()`
- `defer wg.Done()` не первой строкой → потенциальный deadlock при панике
- Замыкание на переменную цикла — все горутины видят одно значение
- Без `wg.Wait()` — main уйдёт, горутины не успеют
