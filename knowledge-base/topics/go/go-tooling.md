# Go tooling — команды go (памятка)

## TL;DR
`go run` — это меньшая часть. Перед каждым коммитом гонять ритуал из 4 команд:
`gofmt -w` → `go vet` → `go test -race` → `go build`.

## Где разобрано подробно
- `go help <команда>` (напр. `go help build`)
- `pkg.go.dev/cmd/go`

## Правило путей
**Всегда указывать пакет (папку), не файл:**
```
go run ./cmd/goscout          ✅ соберёт все .go в пакете
go run main.go                ❌ только один файл — упадёт, если в пакете несколько файлов
```
- `.` = текущий пакет
- `./...` = все пакеты проекта рекурсивно

## 1. Запуск и сборка
| Команда | Что делает |
|---------|-----------|
| `go run ./cmd/goscout` | компилирует во временный бинарник и запускает (удаляет после) |
| `go build ./cmd/goscout` | компилирует в постоянный бинарник в текущей папке |
| `go build ./...` | собрать ВЕСЬ проект, без запуска — проверить, что всё компилится |
| `go install ./cmd/goscout` | собрать и положить в `$GOBIN` (звать из любой папки) |

## 2. Модули и зависимости
| Команда | Что делает | Когда |
|---------|-----------|-------|
| `go mod init <module>` | создаёт `go.mod` | один раз при старте проекта (уже сделано) |
| `go mod tidy` | добавляет недостающие / убирает лишние зависимости | после правки `import` сторонних пакетов |
| `go get <pkg>` | скачать внешнюю зависимость в `go.mod` | при подключении чужой библиотеки |
| `go mod download` | скачать всё из `go.mod` в кэш | редко руками; делает CI |

- `go.mod` — список зависимостей модуля. `go.sum` — хеши зависимостей (защита от
  supply chain атак: проверка, что скачано именно то). Оба коммитятся в git.
- Команды `go init` НЕТ — есть `go mod init`.
- Сейчас зависимостей нет (всё stdlib), `tidy`/`get` почти не нужны.

## 3. Качество кода — ритуал перед коммитом
| Команда | Что делает |
|---------|-----------|
| `gofmt -l ./cmd/goscout` | список плохо отформатированных файлов (`-l`=list, пусто=ок) |
| `gofmt -w ./cmd/goscout` | ИСПРАВИТЬ форматирование на месте (`-w`=write) |
| `go fmt ./...` | то же `gofmt -w` для всех пакетов (обёртка) |
| `go vet ./...` | статический анализ: подозрительная логика (забытый cancel, неверный Printf) |

- **`gofmt`** = про ВИД (отступы, переносы). В Go один канонический стиль, не обсуждается.
- **`go vet`** = про подозрительную ЛОГИКУ. Компилятор пропустил, но «выглядит как баг».

## 4. Тесты
| Команда | Что делает |
|---------|-----------|
| `go test ./...` | все тесты проекта |
| `go test -v ./...` | verbose — каждый подтест (`=== RUN`, `PASS`) |
| `go test -race ./...` | детектор гонок — ОБЯЗАТЕЛЕН для concurrency |
| `go test -run TestX ./...` | только тесты по маске имени |
| `go test -cover ./...` | покрытие тестами в % |

## Ежедневный ритуал (делать рефлекторно)
**Во время разработки:** `go run ./cmd/goscout dns localhost`

**Перед каждым `git commit`, в этом порядке:**
```
gofmt -w ./...           # 1. форматирование
go vet ./...             # 2. статический анализ
go test -race ./...      # 3. тесты с гонками
go build ./...           # 4. всё собирается
```
Это ровно то, что делает CI (`.github/workflows/`) при пуше. Гонять локально —
чтобы CI не краснел на GitHub (рекрутеры видят красные галочки).

## Ключевые термины (English)
- `go vet` — static analysis (статический анализатор)
- `gofmt` — canonical code formatter (форматтер)
- `-race` — data race detector (детектор гонок)
- `go.mod` / `go.sum` — module manifest / dependency checksums
- `supply chain attack` — атака через подмену зависимости (от неё защищает `go.sum`)
- `package path` vs `file path` — `./cmd/x` vs `main.go`
