# context

## TL;DR
`context.Context` — стандартный «сигнал стоп» для набора горутин: таймаут / отмена,
распространяется вниз по цепочке вызовов. Под капотом отмена доставляется через
закрытие канала.

## Где разобрано подробно
- `pkg.go.dev/context`
- `gobyexample.com/context`, `/timeouts`

## Минимальный пример
```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()                       // ОБЯЗАТЕЛЬНО — освобождает таймер, иначе leak

// прокидываем ctx вниз: runDNS → горутина → LookupHost
addrs, err := net.DefaultResolver.LookupHost(ctx, domain)  // прервётся при отмене

select {
case res := <-results:
    // данные пришли
case <-ctx.Done():                   // канал ЗАКРЫЛСЯ → таймаут/отмена
    return
}
// ctx.Err(): почему закрылся — context.DeadlineExceeded | context.Canceled
```

## Личный опыт

### Что я понял не сразу
- **`ctx.Done()` — это КАНАЛ** (`<-chan struct{}`), а не функция-проверка. Пока контекст
  жив — канал открыт и пуст, приём блокируется. Таймаут/отмена → context САМ закрывает
  канал → приём из закрытого возвращается мгновенно → срабатывает `case <-ctx.Done()`.
  Отмена доставляется именно через закрытие канала, никакой магии.
- **Я ничего не пишу и не закрываю в `ctx.Done()`** — это делает context. Я только читаю.
  Тип `<-chan struct{}` — receive-only, компилятор не даст туда писать (защита).
- **`struct{}` — пустая структура, 0 байт.** Канал-сигнал: важен ФАКТ закрытия, не значение.
  Поэтому `case <-ctx.Done():` пишут БЕЗ присваивания. (Тот же `struct{}` — для set:
  `map[K]struct{}`.)
- **Таймаут = потолок (дедлайн), не задержка.** Быстрый ответ (даже ошибка «нет домена»)
  приходит мгновенно. Таймаут стреляет, только когда ответа НЕТ вообще дольше дедлайна.
  Ошибка резолва ≠ таймаут: первое — сервер ответил «нет», второе — сервер молчит.
- **`ctx` — всегда ПЕРВЫЙ параметр функции** (конвенция Go, видно во всём stdlib).
- **Параллельность даёт `go`, отменяемость даёт context.** Это разные вещи. `LookupHost`
  и с ctx, и без — обе синхронные блокирующие; ctx лишь добавляет «кнопку стоп».

### На чём попадался
- `task-07`: `defer cancel()` сначала воспринял как «закрыть заранее». Наоборот —
  вызывается при ВЫХОДЕ из функции, освобождает таймер ВСЕГДА (даже если успели за 2с,
  иначе таймер тикает вхолостую до дедлайна = resource leak). `go vet` ругается, если
  cancel от WithTimeout не вызван.
- `task-07`: при общем таймауте `select` со `case <-ctx.Done()` в цикле сбора надо
  ВЫХОДИТЬ (`return`), а не `continue` — закрытый канал «вечно готов», иначе цикл
  крутит timeout N раз вхолостую (см. [[channels]] про закрытый канал).

### Подводные камни
- Забыл `defer cancel()` → утечка таймера/горутины контекста.
- Общий таймаут отбрасывает опоздавшие результаты, даже если они уже в буфере канала
  (выбор в `select` случайный). Осознанный trade-off, не баг.

## Ключевые термины (English)
- `context` — носитель сигнала отмены/таймаута и дедлайнов
- `context.Background()` — корневой пустой контекст, отправная точка
- `WithTimeout` / `WithCancel` — производные контексты с дедлайном / ручной отменой
- `cancel function` — освобождает ресурсы контекста, зовётся через `defer`
- `Done()` — receive-only канал, закрывается при отмене
- `DeadlineExceeded` / `Canceled` — причины из `ctx.Err()`
- `deadline` — потолок ожидания, не фиксированная задержка
- `empty struct` `struct{}` — тип в 0 байт, для сигналов и множеств
