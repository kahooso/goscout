# Bash — механика (разбор кейса 1.4)

> Записано Claude по итогам сессии, потому что разбор шёл долго и знание рисковало
> потеряться. Конспект своими словами пользователь пишет отдельно — этот файл его не заменяет.

## Четыре столпа

1. **Всё есть команда, у команды есть код возврата.** `0` — успех, не `0` — неудача.
2. **Управление потоком строится на кодах возврата, а не на «истине».** `if` запускает
   команду и смотрит её код.
3. **Данные текут потоками:** stdin (0), stdout (1), stderr (2).
4. **Bash сначала подставляет текст, потом разбирает строку на слова.** Отсюда все
   правила про кавычки.

## Пять механик, которые объясняют остальное

**`[` — это команда, а не синтаксис.** `type [` и `ls -l /usr/bin/[` это показывают.
Пробелы обязательны, потому что `[` — имя команды, а `]` — её обязательный последний
аргумент.

**`if` смотрит на код возврата; `0` = успех.** Инверсия относительно привычной логики.
В `if` можно поставить любую команду: `if grep -q ERROR file; then ...`.

**Кавычки обязательны:** подстановка идёт ДО разбора на слова. `[ -f $f ]` при
`f="my file.log"` превращается в три аргумента и падает. Правило: `"$var"` всегда.

**Три потока.** `>` перезапись, `>>` дописывание, `2>` только ошибки, `|` соединяет
stdout левой команды со stdin правой.

**Три условия для `./script.sh`:** шебанг, право `x`, префикс `./` (текущего каталога
нет в `PATH` — намеренно, иначе подложенный файл с именем `ls` запускался бы сам).

## `set -euo pipefail`

Первая строка любого серьёзного скрипта:
- `-e` — остановиться на первой команде с ненулевым кодом;
- `-u` — ошибка при обращении к несуществующей переменной (ловит опечатки; классика
  катастрофы — `rm -rf "$dir/"` при опечатке в имени);
- `-o pipefail` — конвейер провален, если упало любое звено, а не только последнее.

**Что ломается при добавлении:** `mode="$1"` при запуске без аргументов падает с
`unbound variable` ещё до проверки `$#`. Лечится `${1:-}`. Команды, для которых
«не нашёл» — нормальный исход (`grep`), нужно прикрывать `|| true`.

## Коды возврата — это интерфейс, а не отчёт об аварии

`0` = «да, нашёл, получилось»; ненулевое = «нет». `grep` различает три исхода:
`0` нашёл, `1` не нашёл (не авария), `2` не смог прочитать файл. Именно поэтому
работает `if grep -q ...`.

Правило: **человеку — текст в stderr, программе — число на выходе.**
В функции — `return 1`, а не `exit 1` (`exit` убивает весь скрипт).

## Ошибки, допущенные в этой сессии

| Ошибка | Класс |
|---|---|
| `local file = "$1"` — пробелы вокруг `=` | рецидив: то же правило читал в кейсе |
| `cat file \| grep X \| wc -l` вместо `grep -c X file` | лишние звенья конвейера |
| Изменил `sort -u` → `sort` в общей функции — сломал режим `scan` | **регрессия: правка общей зависимости под одного потребителя** |
| `wc -l < grep ... file` | `<` ожидает имя файла, не команду |
| Дублирование регулярки в двух функциях | правка потребуется в двух местах |

Регрессия — та же тема, что слабость №1 по roadmap (тестирование): проверка заняла бы
один запуск `scan`.

## Связки с Go / outpost

- `exit 1` в bash ↔ `exitError` + вынос `os.Exit` в `main` (task-13): мост
  «ошибка внутри программы → код процесса», с двух сторон.
- `local` + аргументы функции ↔ `run(args []string, s streams) error` вместо глобального
  состояния: функция зависит только от того, что ей передали.
- «Не нашёл» отдельным кодом ↔ `errors.Is`: вызывающий должен различать исходы
  программно, а не парсить текст.

## Ключевые термины (English)

exit code / return code — код возврата · shebang — строка интерпретатора ·
standard streams (stdin/stdout/stderr) — стандартные потоки · pipe — конвейер ·
word splitting — разбор строки на слова · command substitution `$(...)` — подстановка
команды · parameter expansion `${VAR:-default}` — подстановка значения по умолчанию ·
regression — регрессия
