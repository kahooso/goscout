# Стенд под кейс 1.11: сеть, загрузка, TLS — troubleshooting

Разбор вечера, когда развёртывание стенда под Wazuh (кейс 1.11) встало на банальностях:
SSH не подключался ~1.5 часа, VM грузилась в boot manager руками, чекер не качался.
Контента SIEM тут нет — это **переносимые уроки диагностики**, которые пригодятся и на
собеседовании, и в кейсе 1.9 (сетевые интерфейсы), и в любой работе с сетью.

Ни одна из трёх проблем не была «сложной» — все три держались на **одной опечатке /
одном пропущенном слое**. Дорого стоило не незнание, а доверие к пересказу вместо сырого вывода.

## 1. Таксономия сетевых ошибок — читать первым делом

Три разных ответа при попытке соединиться делят пространство причин на три непересекающиеся части:

| Ответ | Что физически произошло | Куда смотреть |
|---|---|---|
| **Connection refused** | TCP-пакет дошёл до хоста, но порт закрыт — никто не слушает | сервис не запущен / не тот порт |
| **Connection reset** | Соединение приняли, потом оборвали (RST) | адрес есть, но за ним пусто / сервис отшивает / проброс бьёт в несуществующий IP |
| **Timeout / зависание** | Пакет ушёл и пропал, ответа нет вообще | пакет уходит не туда / хост молчит / MTU режет большие пакеты |

За этот вечер симптом прошёл путь **reset → hang**, и это было **движением вперёд**:
reset = проброс слал на несуществующий `198.168.250.x`; после правки на `192.x` стало
зависание = адрес правильный, но подсеть NAT-сети всё ещё `198.x`, и пакет уходил в никуда.
Смена ошибки — это сигнал, что предыдущий слой починен, а не что стало хуже.

## 2. Бисекция: тестируй с заведомо здоровой стороны

Главный приём вечера. Чтобы понять, где ломается, надо разрезать систему на границе
и проверить одну половину, лежащую целиком по одну сторону:

- **SSH к самому себе изнутри гостя** (`ssh user@localhost`) — не выходит за пределы VM,
  снимает подозрение с сети и гипервизора. Работает → виноват путь снаружи, не sshd.
- **Тот же запрос с заведомо здоровой машины.** Тот же `wget`-URL с Windows (где полный
  набор публичных корневых CA) дал ту же ошибку сертификата → виноват не гость, а сервер.
- **Сырой TCP + чтение баннера** проверяет сервис без логина: `sshd`/HTTP/SMTP шлют
  приветствие сразу при коннекте. Получил `SSH-2.0-OpenSSH...` через проброс — значит весь
  путь Windows → VBox → гость → sshd жив, и пароль не нужен для доказательства.

## 3. VirtualBox: три независимые «дороги» сети

Их путали весь вечер. Они не заменяют друг друга:

- **VM ↔ VM** (по внутренней сети, напр. `192.168.250.10 ↔ .11`) — так работает сам сервис
  (агент шлёт события серверу). Машины на одной NAT-сети видят друг друга **по L2 напрямую**,
  минуя NAT-движок — поэтому эта связь работает, даже если подсеть NAT-сети настроена криво.
- **Проброс портов** (`ssh -p 2225 user@127.0.0.1`) — для **тебя-админа** с хоста. `127.0.0.1`
  тут = твоя машина; VBox слушает порт хоста и проталкивает соединение в гостя. Обслуживает
  его **NAT-движок**, который работает в пределах своей подсети.
- **Ключевое правило:** статический IP гостя и Guest IP в правиле проброса **обязаны лежать
  в подсети самой NAT-сети**. Если NAT-сеть — `198.168.250.0/24`, а гости и правила — `192.x`,
  то VM↔VM работает (L2), а проброс и интернет — нет (движок не маршрутизирует в чужую подсеть).

Диагноз командной строкой (быстрее и честнее кликов по GUI):
`VBoxManage list natnetworks` — покажет `Network:`/`Gateway:` подсети;
`netstat` на хосте — слушает ли VBox порт проброса (если да, правило живо).

## 4. UEFI: почему грузит в boot manager и как чинить раз навсегда

Цепочка загрузки: **прошивка (UEFI) → загрузчик (grub) → ядро**. Прошивка знает, какой
загрузчик грузить, из записи в **NVRAM**. Запись потеряна/не создалась (в VirtualBox NVRAM
плохо переживает перезагрузки) → прошивка сваливается в ручной Boot Manager.

Фикс, не зависящий от NVRAM: положить grub в **резервный путь** `\EFI\BOOT\BOOTX64.EFI` —
его прошивка пробует всегда, когда записи не сработали (по нему же грузятся флешки/live-образы):
```bash
sudo mkdir -p /boot/efi/EFI/BOOT
sudo cp /boot/efi/EFI/debian/grubx64.efi /boot/efi/EFI/BOOT/BOOTX64.EFI
```

## 5. TLS: приватный CA и битый файл

- `certificate is not trusted / unknown issuer` при `wget https://...` — сертификат подписан
  **приватным CA**, которого нет в публичных хранилищах. Проверено бисекцией: **Windows тоже
  его отверг** (`SEC_E_UNTRUSTED_ROOT`). Значит `apt install ca-certificates` не поможет — там
  только публичные корни. Правильно — добавить корень организации в доверенные; на один раз —
  скачать с `--no-check-certificate` (wget) / `-k` (curl).
- **Осознанная дыра, не рефлекс.** `--no-check-certificate` выключает проверку подлинности —
  сердце TLS. MITM мог бы подсунуть свой бинарник, а его потом запускают через `sudo`.
  Терпимо для внутреннего ресурса, но в бою — добавлять CA и сверять контрольную сумму.
- **Битый TLS → пустой файл.** Незавершённая загрузка оставила `checker` **нулевого размера** —
  поэтому «скачался, но не запускается». Правило: после скачивания проверять
  `file <файл>` (должно быть `ELF ... executable`, а не `HTML`) и размер, до `chmod +x`.

## 6. Мета-урок вечера

- **Сырой вывод > пересказ.** «Всё окей», «Guest IP правильный», «IP на обеих верные» —
  каждый раз пересказ прятал баг; находил его только дословный вывод команды / скриншот.
  Проси показать, а не подтвердить.
- **Одна опечатка, размноженная копипастом, живёт в нескольких слоях.** `198` вместо `192`
  сидело и в правилах проброса, и в определении NAT-сети. Чинишь одну копию — система висит
  на второй, невидимой. Сетевой адрес сверяют **посимвольно во всех слоях**, а не «в целом»
  (глаз проглатывает `192↔198`, `250↔205`, `.10↔.01`). Уже третий случай ошибки ручного
  переноса (см. `/pt-intern/home` и `ilbc` vs `libc` в журнале).

## 7. Сетевые интерфейсы и DNS (Case 1.9)

**Два стека на один интерфейс.** `enp0s3` может управляться либо **ifupdown** (файл
`/etc/network/interfaces`, команда `systemctl restart networking`), либо **NetworkManager**
(nmcli / настройки GNOME). Это конкуренты: NM игнорирует интерфейс, если его застолбил ifupdown.
DebianCLI в лабе — ifupdown, DebianGUI — NetworkManager. Чекер проверяет состояние своего стека,
поэтому важно, каким именно ты настраиваешь.

**static vs dynamic читается в `ip a`:** слово `dynamic` + конечный `valid_lft` (напр. 86400sec)
= адрес по DHCP (арендован); нет `dynamic` + `valid_lft forever` = статический. Само число IP
ни о чём не говорит — VBox по DHCP всегда выдаёт `.15`, и статика на тот же `.15` выглядит так же.

**NetworkManager: имя ≠ идентификатор.** `con-name` — просто ярлык, не уникален; можно наплодить
тёзок (у меня вышло два `static-enp0s3`). Уникален **UUID**. Поэтому `nmcli connection up <имя>`
при дублях неоднозначен — адресуй/удаляй по UUID. Колонка **DEVICE** в `nmcli connection show`
= какой профиль реально сидит на карте (`--` = ни один).

**DHCP — протокол клиент↔сервер.** Клиент на машине широковещательно просит конфиг, сервер
отвечает (DORA: Discover-Offer-Request-Ack) и выдаёт IP + маску + шлюз + DNS + срок аренды.
Сервер — **общий на сегменте**, не персональный: роутер / корп-сервер / у VBox — сам NAT-движок.

**DNS-диагностика в три слоя** (спасла вечер):
1. связь — `ping <IP>` (напр. `1.1.1.1`);
2. резолв — `getent hosts <имя>` (использует `/etc/resolv.conf` + `nsswitch`);
3. у кого спрашиваем — `cat /etc/resolv.conf`, активен ли `systemd-resolved`.
Если связь есть, а резолв мёртв на **всех** серверах — виноват слой ниже конфига гостя.

**Killer этой сессии: DNS полностью мёртв в NAT-движке VirtualBox.** Из гостя не резолвилось
ничего (ни `1.1.1.1`, ни `8.8.8.8`, ни `10.0.2.3`) при живом `ping 1.1.1.1` и при том, что
Windows-хост резолвит всё. То есть порт 53 из гостя не ходит вообще — методичкин совет «поменяй
DNS на 1.1.1.1» тут бесполезен.
- **Правильный фикс:** `VBoxManage modifyvm "<VM>" --natdnshostresolver1 on` + ребут VM —
  заставляет VBox резолвить через хостовый API (который работает).
- **Обход без ребута:** пин имени в `/etc/hosts` (`178.248.239.151 global.ptsecurity.com`).
  Работает, потому что в `nsswitch.conf` `hosts: files ... dns` — файл проверяется РАНЬШЕ DNS.
  Это и аварийный обход, и, к слову, классический вектор атаки (подмена hosts уводит на чужой IP).

**Guest-side помощь через SSH (когда стенд не пускает, а пользователь застрял и дал доступ).**
Проброс `127.0.0.1:1337 → 22` + неинтерактивный пароль через `SSH_ASKPASS`-хелпер (OpenSSH ≥8.4,
`SSH_ASKPASS_REQUIRE=force`) позволяет Claude зайти в гостя и чинить изнутри. `sudo` — через
`echo '<pароль>' | sudo -S -v` (прогреть таймстамп, дальше `sudo` без `-S`). **После — удалить
файл-хелпер с паролем.** Делать так только по явной просьбе и для инфра-блокера, не для решения
зачёта за пользователя. Полный протокол — скилл `pt-course`, раздел про инфраструктуру стенда.

## 8. Корень саги `198`/`192`: DHCP-сервер сети (найдено 2026-09-19)

Опечатка `198` вместо `192` жила в **трёх** местах, и последнее нашлось только в конце:
1. правила проброса (Guest IP) — исправлено руками;
2. подсеть самой NAT-сети (`Network`) — исправлено `natnetwork modify --network`;
3. **DHCP-сервер сети** — остался на `198.168.250.x`, хотя сеть уже `192.168.250.0/24`.

Пункт 3 и был скрытым источником всего: `natnetwork modify --network` меняет CIDR сети, но **не
трогает связанный DHCP-сервер**. Поэтому любая VM, бравшая адрес по DHCP, получала `198.168.250.x`
(чужая подсеть → нет шлюза → мёртвый DNS, зависший apt). Статические VM (Wazuh) не страдали.

Проверка и фикс:
```powershell
VBoxManage list dhcpservers                       # видно NetworkName + Dhcpd IP/диапазон
VBoxManage dhcpserver modify --network=NAT `
  --server-ip=192.168.250.2 --lower-ip=192.168.250.100 --upper-ip=192.168.250.200 `
  --netmask=255.255.255.0 --set-opt=6 8.8.8.8      # опция 6 = DNS
```
**Правило: здоровье сети = совпадение ТРЁХ вещей — подсеть сети = адрес гостя = диапазон DHCP.**
Чинишь сеть — сверяй все три, а не только CIDR.

**Выбор режима адаптера — под образ.** Адрес, зашитый в гостя, диктует режим: статик `10.0.2.15`
(plain-NAT-native) → обычный NAT; OVA под `192.168.250.x` → NAT Network. Не «какой NAT лучше»,
а «какой нужен ЭТОЙ машине». Читается из `ip a` гостя, а не угадывается.

## 9. Promiscuous Mode — почему мост MikroTik в VBox не пингуется (2026-09-23, кейс 2.7 VLAN)

**Стоило двух ночей и ~5 часов.** Симптом: три MikroTik-моста в треугольнике, конфиг верный (мост,
порты, IP, rstp), а **broadcast-шторм идёт (1472 pps), unicast-пинг между роутерами = 100% loss.**

Корень — **Promiscuous Mode = `Deny` (дефолт адаптера VBox).** При Deny адаптер отдаёт в гостя только
кадры **на свой MAC + broadcast/multicast**. А MikroTik-**мост** (L2-коммутатор) обязан принимать кадры
на **чужие MAC** — те, что «за мостом» (адрес `br1` ≠ MAC физ-порта; плюс транзит между портами). Deny
их режет. Отсюда: broadcast (ARP, шторм) доставляется всегда → шторм есть; unicast-ответ на MAC моста,
пришедший на «не тот» порт, отбрасывается → пинг 100%.

**Диагностический якорь:** голый тест «IP прямо на `ether`» (без моста) работает (кадры на свой MAC),
а как только IP переезжает на `br1` и мост форвардит — 100% loss. Это отличает проблему промискуитета
от проблемы конфига.

**Фикс:** Promiscuous = **Allow All** на КАЖДОМ адаптере каждой мост/switch-ВМ (VM → Настройки → Сеть →
Адаптер → Дополнительно → Неразборчивый режим → Разрешить всё; или `VBoxManage modifyvm <vm>
--nicpromiscN allow-all` при выключенной ВМ). **L3-роутеру (кейс 2.8) НЕ нужен** — роутер принимает
кадры на свой gateway-MAC. Правило: **L2-мост → Allow All; L3-роутер → Deny.**

**Горячая правка НЕ применяется.** `controlvm nicpromiscN` (и `nicN intnet <name>`) на живой ВМ ставит
настройку в конфиг, но к работающему адаптеру не применяется (полу-привязка: приём есть, передача нет).
Нужен **полный power-cycle** (poweroff → startvm); гостевой `reset` адаптер НЕ пересобирает. Проще —
задать до старта ВМ. Причину нашёл **пользователь** (внешняя наводка), не Claude.

**Три разных «мост», не путать:** (1) RouterOS bridge (`br1`, L2-коммутация); (2) VBox «Bridged Network»
адаптер (выход ВМ в физсеть хоста); (3) promiscuous (фильтр приёма кадров). Слово одно — вещи разные.

## 10. NAT-стенд: диагностика уплинка (кейс 2.8)

L3-роутинг + NAT, промискуитет НЕ нужен. Затык был в уплинке `MikroTik2 ether3 (Bridged) → интернет`.

**Порядок диагностики уплинка (сверху вниз):**
1. Есть ли адрес на внешнем интерфейсе? `/ip address print` — на `ether3` должен быть `192.168.X.X`.
   Пусто → нет уплинка, дальше не идёт.
2. DHCP-клиент: `/ip dhcp-client print` — статус **`bound`** с адресом, интерфейс **`ether3`**.
   `stopped`/`invalid`/`interface=*2` → клиент **на не том интерфейсе** (был баг: висел на `*2`, не на
   `ether3`). Фикс: `remove [find]` + `add interface=ether3 disabled=no`.
3. Дефолт-маршрут: `/ip route print` — `0.0.0.0/0` должен быть **активен** (без флага `I`). `Is`
   (inactive) = шлюз недостижим (нет адреса из его подсети на интерфейсе).
4. Сам роутер в интернете? `/ping 8.8.8.8` с MikroTik2. Только потом — хост за ним.

**Bridged поверх Wi-Fi** (Realtek 8822CE) в этот раз DHCP пропустил — но это везение: Wi-Fi-мост капризен
(AP часто режет кадры с MAC ≠ MAC станции хоста). `ether3` не получает адрес при `link-ok` → первый
подозреваемый именно это; запасной план — VBox NAT-режим на `ether3`. **Адрес домашнего роутера** = шлюз
по умолчанию хоста (`ipconfig` → «Основной шлюз»); Bridged-ВМ попадает в ту же физсеть, что и хост.

## Ключевые термины (English)

- **promiscuous mode** — режим адаптера «принимать кадры и на чужие MAC»; нужен L2-мосту, не L3-роутеру
- **masquerade / src-nat** — подмена адреса источника уходящего пакета (прячет внутреннюю подсеть)
- **dst-nat / port forwarding** — подмена адреса/порта назначения (проброс к внутреннему сервису)
- **connection refused / reset / timeout** — порт закрыт / оборвано RST / ответа нет
- **port forwarding** — проброс: хост-порт → `guestIP:guestPort` через NAT-движок
- **NAT Network vs NAT** — общая сеть для нескольких VM (проброс на самой сети) vs per-VM NAT
- **L2 adjacency** — машины одного сегмента видят друг друга по MAC, без маршрутизатора
- **bisection** — деление системы на границе и проверка одной половины
- **banner grabbing** — снятие приветствия сервиса сырым TCP без логина
- **UEFI boot chain** — firmware → bootloader (grub) → kernel; указатель в **NVRAM**
- **fallback bootloader path** — `\EFI\BOOT\BOOTX64.EFI`, последняя попытка прошивки
- **root CA / chain of trust** — доверие сертификату идёт по цепочке к корню, которому доверяет ОС
- **MITM (man-in-the-middle)** — подмена стороны соединения; TLS-проверка защищает именно от неё
- **MTU** — макс. размер кадра; слишком большой режется/теряется → обрыв больших пакетов (TLS)
