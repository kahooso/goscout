# Task-07: Параллельный DNS resolve через каналы + context

## Задание

**Файл:** `cmd/goscout/main.go` (реализовать `runDNS`, заменив заглушку)
**Тесты:** `cmd/goscout/main_test.go` (минимум 3 кейса, с `-race`)

Превратить заглушку `runDNS` в рабочую фичу: параллельный DNS resolve
N доменов с общим таймаутом через context.

### Что должно получиться

```
goscout dns google.com github.com nonexistent.invalid
```
→ запускает по одной горутине на домен, каждая резолвит имя в IP,
результаты собираются в main через канал, общий таймаут через context.

### Требования

1. **Структура результата** — тип `dnsResult` с полями: домен, найденные IP
   (`[]string`), ошибка (`error`). Одна горутина → один `dnsResult` в канал.
2. **Функция резолва** — `resolveDomain(ctx, domain, ch)`:
   - резолвит домен (см. экскурсию по пакету — `net.Resolver.LookupHost`
     с context, НЕ `net.LookupHost` без context — нам нужен таймаут);
   - кладёт `dnsResult` в канал `ch`.
3. **Сбор результатов** — main запускает N горутин, затем в цикле собирает
   N результатов через `select`:
   - `case res := <-ch:` — получили результат, печатаем;
   - `case <-ctx.Done():` — таймаут, прекращаем ждать остальные, выходим.
4. **Контекст** — `context.WithTimeout`, дефолт 5s. `defer cancel()` обязателен.
5. **Вывод** — по результату на строку: домен → IP или домен → ошибка.

### Тесты (table-driven, 3+ кейса)

Тестировать `resolveDomain` (не main). Каналы → читаем результат из канала в тесте.
- happy: валидный домен (например `localhost` — резолвится без сети, стабильно
  в тестах) → непустой список IP, без ошибки;
- злой: заведомо несуществующий домен (`.invalid` TLD зарезервирован под это)
  → ошибка не nil;
- граничный/таймаут: context с уже истёкшим таймаутом (`0` или отменённый
  cancel) → горутина должна завершиться с ошибкой контекста, не зависнуть.

`go test -race ./cmd/goscout/` — обязательно с `-race` (concurrency).

## Моё решение

Реализовал `runDNS` + `resolveDomain` в `cmd/goscout/main.go`, тесты в `main_test.go`.

- `dnsResult{domain, addrs []string, err}` — результат одной горутины.
- `runDNS`: `context.WithTimeout(5s)` + `defer cancel()`; **buffered-канал**
  `make(chan dnsResult, len(args))`; **ДВА раздельных цикла** — сначала запуск всех
  горутин (`go resolveDomain` на каждый домен), потом сбор N результатов через `select`.
- `select` в сборщике: `case res := <-ch` (печать; ошибка → early-return-стиль `continue`,
  без `else`) / `case <-ctx.Done(): return`.
- `resolveDomain`: `net.DefaultResolver.LookupHost(ctx, domain)`, результат
  (включая ошибку) **ВСЕГДА** летит в канал — иначе счётчик сборщика не сойдётся.
- Тесты: table-driven, 3 кейса. happy `localhost` (+ условная проверка `len(addrs)>0`
  только при `!wantErr`), злой `nonexistent.invalid`, таймаут `WithTimeout(ctx, 0)`.
  Проверка `(res.err != nil) != tc.wantErr`. `go test -race` — зелёные.

Прогон: `localhost`/`github.com`/`nonexistent.invalid` — все обработаны, ошибочный
мгновенно (не висит 5с). `gofmt`/`vet`/`-race`/`build ./...` чисто.

## Ошибки и трудности

**Концептуально (новое в сессии):** многопоточности в C/Go раньше не трогал —
race condition / mutex / atomic / deadlock были новыми словами. Разбирали с нуля
перед каналами. См. [[channels]], [[context]].

Конкретные баги по ходу (каждый — отдельная итерация ревью):
1. **Тип канала не совпал:** `chan string` vs сигнатура `chan dnsResult`. Решил, что
   течёт по каналу — структура (иначе теряешь чей результат и была ли ошибка).
2. **Одна горутина с циклом внутри** вместо `go` внутри цикла → последовательно, не
   параллельно. `go` оборачивает один вызов, не весь цикл.
3. **Слил цикл запуска и сбора в один** → блокировался на каждой итерации. Нужно два.
4. **nil-указатель `var r *net.Resolver`** — «работало» случайно (методы `net.Resolver`
   специально терпят nil-receiver = дефолт). Заменил на `net.DefaultResolver`.
   Понял: вызов метода на nil-указателе законен, паника — только при разыменовании
   поля внутри метода.
5. **early-return в горутине съел ошибочные результаты** (`if err != nil { return }` без
   отправки) → рассинхрон N запущено / <N собрано → зависание до таймаута. Чинится:
   отправлять `dnsResult` ВСЕГДА (ошибка — валидный результат в поле `err`).
6. **`for _, d := range` + печать `d` при таймауте** — `d` не соответствует зависшему
   домену (порядок канала ≠ порядок args). Откатил к `for range` + молчаливый return.
7. **Тесты — flaky `select`:** в таймаут-тесте `select` с закрытым `ctx.Done()` +
   готовым `ch` → случайный выбор → падал через раз. Убрал `select`, читаю `<-ch`
   напрямую (вызов синхронный, результат уже в буфере). Живая иллюстрация «select при
   двух готовых case выбирает случайно».
8. **`len(addrs)>0` во всех кейсах** валил ошибочные (где адресов и не должно быть).
   Сделал условной: `if !wantErr && len(addrs)==0`.

deadlock vs goroutine leak спутал — развёл (см. [[channels]]).

## Что бы сделал иначе

- Сразу держать в голове «два цикла: запуск ‖ сбор», а не сливать в один.
- Не применять early-return там, где функция обязана прислать результат на каждый запуск.
- В тестах не лепить `select`, если вызов синхронный — читать канал напрямую.
- Идея на потом: печатать домены в таймауте через `seen := map[string]bool` (+паттерн,
  после A0).

## Ключевые пакеты и паттерны

- `context.WithTimeout` + `defer cancel()` — таймаут на группу горутин.
- `net.DefaultResolver.LookupHost(ctx, ...)` — резолв с контекстом.
- Паттерн **fan-out/collect**: N горутин-producer → buffered-канал → сборщик считает N.
- buffered-канал на `len(N)` против goroutine leak.
- `select` с `case <-ctx.Done()` — данные ИЛИ таймаут.
- table-driven тесты `-race`, условные проверки по `wantErr`.
- go tooling — ритуал перед коммитом, см. [[go-tooling]].
