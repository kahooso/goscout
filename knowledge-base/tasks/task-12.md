# Task-12: аудит `ports` перед тегом v0.1 — отмена, инъекция, тесты

Первая задача после закрытия блока A0. Не учебная тема, а **доведение продукта**:
найденные на ревью дефекты `PortProbe.Run` + подготовка репозитория к тегу.
Работа шла в `Desktop/outpost` (публичный репо), запись — здесь.

## Задание

Из аудита 2026-07-28: `PortProbe.Run` принимает `ctx` и **не использует его** — воркеры
не смотрят на отмену, а результат сканирования одинаков для честного и для оборванного
запуска. Три подпункта:

1. воркер должен уважать отмену (`net.DialTimeout` → `Dialer.DialContext`);
2. сборщик должен узнавать об отмене;
3. при отмене возвращать `Output: nil`, `Error: ctx.Err()`.

## Моё решение

**Подпункт 1** (сделан в предыдущей сессии): `net.DialTimeout(...)` → `net.Dialer{Timeout: p.Timeout}`
+ `d.DialContext(ctx, "tcp", addr)`.

**Подпункт 2 — где обнаруживать отмену.** Разобрали два варианта:

| | `select` внутри цикла сборщика | `ctx.Err()` после цикла |
|---|---|---|
| момент выхода | самый ранний | после сбора всех результатов |
| детерминизм | нет: при двух готовых ветках `select` кидает монетку | полный |
| риск зависнуть | нет | нет |

Выбрал второй. Обоснование измерением: `select` при двух готовых ветках дал 489/511
на 1000 итераций — тест «отменённый ctx → ошибка» на первом варианте падал бы примерно
в половине прогонов при одном порте.

Зависнуть цикл не может по построению: воркер шлёт `portResult` **вне** `if isOpen`
(один job → ровно один send), а после смерти контекста `DialContext` возвращается
мгновенно (замер: 0 с / 552 мкс вместо `Timeout: 5s`).

**Подпункт 3:** второй `return` с `Error: ctx.Err()` и без `Output`.

**Инъекция дайлера.** Чтобы тест на отмену не зависел от сети, повторил приём, который
за день до этого применил к DNS: интерфейс `Dialer` с одним методом `DialContext`
(сигнатура дословно как у `*net.Dialer`), неэкспортированное поле `dialer` в `PortProbe`,
метод `pick()` с фолбэком на `&net.Dialer{Timeout: p.Timeout}`.

**Раскладка по файлам.** `main.go` (285 строк) разрезан по домену:
`probe.go` (контракт + раннер), `dns.go`, `ports.go`, `input.go` (`readTargets` + `parsePorts`),
`http.go`, `main.go` (только флаги и switch, 76 строк). Тесты разложены так же.

## Ошибки и трудности

**Главный провал сессии — снова тесты**, третий раз подряд после retest-01.

1. **Проверку `ctx.Err()` поставил не в то место** — сразу после запуска воркеров, до цикла
   сборщика. Она фиксировала состояние контекста **на старте** скана, а весь скан идёт ниже.
   Доказано прогоном модели: дедлайн 10 мс, скан 101 мс, вернулось `err = <nil>`.
   Дефект остался нетронутым, хотя строка появилась.

2. **Первый тест на отмену не проверял отмену вообще.** `PortProbe{dialer: stubDialer{}}` —
   без `Ports`, поэтому `Run` выходил на первой строке с `no ports to scan`, а проверка
   `res.Error == nil` радовалась любой ненулевой ошибке. Заглушка не вызывалась ни разу.
   **Ранний выход как источник ложно-зелёного** — новая для меня форма той же болезни,
   что тавтологии в retest-01.

3. **Мутационный критерий провален.** Claude перенёс проверку обратно наверх — тесты
   остались зелёными (`ok 2.227s`). Тест не различал рабочую версию и сломанную.

4. **Мёртвый контекст на входе ничего не доказывает.** `context.WithTimeout(ctx, 0)` —
   контекст умер **до** вызова; такой тест зелёный на обеих версиях кода. Чтобы убить
   мутанта, контекст обязан умирать **по ходу** скана.

5. **Заглушка нарушала контракт зависимости.** `return nil, ctx.Err()` при живом контексте
   даёт `(nil, nil)` — `Run` посчитал бы порт открытым и вызвал `conn.Close()` на
   nil-интерфейсе (паника). У `net.Dialer` контракт жёсткий: либо соединение, либо ошибка.

**Итог по тесту: писал не я.** После пятой итерации сказал, что устал и не понимаю,
и попросил дописать. Тест `TestPortProbeRunCanceled` (заглушка `slowDialer` с задержкой
200 мс против дедлайна 20 мс) написан Claude, мутация проверена: с проверкой наверху
тест краснеет `Error = <nil>, want context deadline exceeded`.

**Мелочи, пойманные на ревью:**

- Развесил `PortProbe{}.Name()` вместо `p.Name()` — создание пустого значения ради вызова
  метода при живом receiver.
- Занёс `case DNSProbe{}.Name():` в `switch` командной строки. Компилятор перестаёт ловить
  дубликаты веток: проверено — два `case` с одинаковым результатом метода компилируются
  молча, а те же литералы дают `duplicate case "dns" in expression switch`. Плюс имя команды
  это контракт с пользователем, а `Name()` — формат вывода; связывать их нельзя.
- Явные нулевые значения в литералах (`Output: nil`, `Error: nil`) — старая привычка.
- Новые файлы дважды приезжали с CRLF, `gofmt -l` показывал их все. Завёл `.gitattributes`
  (`* text=auto`, `*.go text eol=lf`).

## Что бы сделал иначе

- Сначала спрашивать «что этот тест обязан не пропустить», потом писать `if`. Все три
  провала выше ловятся одним вопросом: **какая поломка кода покрасит эту проверку?**
- Прогонять мутацию сразу, не откладывая: я её так и не прогнал сам ни разу за сессию.
- Перед «зелено, готово» смотреть, дошло ли выполнение до интересной части. Ранний выход
  из-за незаполненного поля структуры виден за секунду, если специально его искать.
