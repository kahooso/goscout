# Task-10: goscout ports — TCP-сканер с worker pool

## Задание

**Файл:** `cmd/goscout/main.go` (наполнить `PortProbe.Run`, добавить поля и helper, подключить CLI-ветку `ports`)
**Тесты:** `cmd/goscout/main_test.go`

Наполнить заглушку `PortProbe.Run` реальным TCP-сканом портов. Новая концепция — **worker pool**.
Стадии: (1) последовательная версия + тест; (2) worker pool; (3) CLI (`parsePorts` + флаги).

---

## Моё решение

**Сделано (стадия 1 — последовательный скан, тест зелёный):**

- `PortProbe` получил поля: `Ports []uint16` (порт влезает ровно в 16 бит — `uint16` это буквально
  «тип порта»), `Timeout time.Duration` (таймаут одного dial).
- `PortProbe.Run(ctx, target)`:
  - guard: `len(p.Ports) == 0` → `Result` с ошибкой;
  - последовательный `for` по портам: `net.JoinHostPort(target, strconv.Itoa(int(port)))` →
    `net.DialTimeout("tcp", addr, p.Timeout)`;
  - `err == nil` → порт open: `open = append(open, strconv.Itoa(int(port)))` **и** `conn.Close()`
    внутри `if` (иначе паника на `nil`-conn);
  - `Result{..., Output: open, Error: nil}`.
- Тест `TestPortProbeRunOpen`: `net.Listen("tcp", "127.0.0.1:0")` поднимает слушатель, ОС выдаёт
  свободный порт, `ln.Addr().(*net.TCPAddr).Port` → сканируем ровно его, ждём в `Output`. Ядро
  ОС завершает handshake даже без `Accept()` → порт виден open. Старый `TestPortProbeRun` оставлен
  как guard-тест (пустой `PortProbe{}` → ошибка).

**Сделано (стадия 2a — worker pool, тесты зелёные -race):**

- `PortProbe.Run` переписан с последовательного `for` на **worker pool**: `const workers = 100`,
  два буферизованных канала на `len(p.Ports)` — `jobs chan uint16` и `results chan portResult`
  (именованный тип `portResult{Port uint16; Open bool}` вместо анонимного struct).
- Порядок: заполнить `jobs` всеми портами → `close(jobs)` → запустить N воркеров (`go func`
  снаружи, `for port := range jobs` внутри) → каждый воркер дайлит и шлёт результат в `results`
  **на КАЖДЫЙ порт** (и open, и closed) → сборщик читает **ровно `len(p.Ports)`** результатов,
  `append` в `open` только для `r.Open`.
- Новый тест `TestPortProbeRunClosed`: `Listen(:0)` → взять порт → **сразу `ln.Close()`** (без
  `defer`, порт нужен закрытым) → скан → ждём `Error == nil` + пустой `Output` + отсутствие deadlock.

**Сделано (стадия 2b — числовая сортировка, тест зелёный):**

- Worker pool отдаёт открытые порты в **непредсказуемом порядке** (кто первый прислал в `results`).
  Собираю их в `open []uint16` (порты остаются числами), сортирую `slices.Sort(open)` **до**
  конвертации в строки, потом в цикле `strconv.Itoa` → `Output []string`.
- Сортировка ЧИСЛЕННО, не строк: `slices.Sort([]uint16)` даёт `80 < 443`, а лексикографическая
  сортировка строк дала бы `"443" < "80"` (посимвольно `'4' < '8'`). Ключ — сортировать пока
  порты числа, конвертировать в строку в самом конце.
- Тест `TestPortProbeRunSorted`: поднять 4 слушателя на `:0`, собрать их порты, отдельной копией
  `slices.Sort` построить ожидаемый порядок, сравнить с `res.Output` через `reflect.DeepEqual`.

**Сделано (стадия 3 — CLI, build/vet/-race зелёные):**

- `parsePorts(s string) ([]uint16, error)`: `strings.Split(s, ",")` → по каждому `strconv.Atoi`
  (с `strings.TrimSpace`) → валидация `MinPort..MaxPort` (1..65535) → `[]uint16`. Функция
  **возвращает** ошибку через `fmt.Errorf(... %w)`, НЕ печатает и НЕ вызывает `os.Exit` (это дело
  вызывающего). Fail-fast: первый битый порт → сразу `return nil, err`.
- Ветка `case "ports"` в `main`: свой `flag.NewFlagSet`, флаги `--ports`/`--timeout`,
  `fs.Parse(os.Args[2:])` → `parsePorts(*portsRaw)` → `fs.Args()` как targets →
  `runProbe(PortProbe{...}, targets, timeout)`. Заглушка `runProbe(PortProbe{},...)` убрана.

**Сделано (унификация вывода):** весь вывод приведён к одному образцу на английском —
stdout = данные, stderr = ошибки; формат ошибки `<команда>: <строчными, без точки>\n`; имя команды
как префикс добавляет тот, кто ПЕЧАТАЕТ (main/runProbe), доменные функции возвращают голую ошибку
через `%w` (без имени функции в тексте). `slog` для CLI не берём — он для сервисов (лог-агрегация),
в терминале его timestamp/level только мешают пайпу. Разбор образца — в [[stdlib-cli]].

## Ошибки и трудности

- **Полная потеря TCP/IP-фундамента за 2.5 недели.** Сессия началась с «я всё забыл» — пришлось
  переактивировать всю базу заново (IP-адрес vs IP-протокол, IP≠UDP, что подтверждает ACK, FIN vs
  тишина). Урок: фундамент выветривается без периодического возврата.
- **Интерфейс vs поля структуры.** Не сходилось: как `PortProbe` может иметь `Ports`/`Timeout`,
  если интерфейс требует `(ctx, target)`. Разобрано: сигнатуру метода диктует интерфейс (параметры),
  поля — своя конфигурация пробы, доступ через receiver `p` (= `this` в C++). Параметры и поля
  ортогональны: «что передали на вызов» vs «чем проба настроена».
- **`conn.Close()` вне `if err == nil` (паника-ловушка, Q3).** На закрытом порту `conn == nil` →
  `Close()` → паника. Сам верно ответил в контрольном, но в коде посадил дважды при правках, чинил.
- **Финальный `return` с `Error` всегда непустым.** Скопировал `errors.New(...)` из guard в
  happy-path return → любой успешный скан считался провалом. Должно быть `Error: nil`.
- **Баг `target`: передал `"127.0.0.1:0"` (адрес слушателя) вместо чистого host.** `JoinHostPort`
  увидел двоеточие в host, решил, что это IPv6, обернул в скобки → мусорный `addr` → `open` пустой.
  Урок: `target` сканера — **всегда голый host**, строка `host:port` — другой предмет.
- **Паника «65к портов на каждый хост».** Накрутил себя: думал, сканируем все 65535. На деле —
  только `p.Ports` (горстка, дефолт 4). 65535 всплыло только в объяснении, зачем нужен worker pool.

**Стадия 2a (сессия 2026-07-06):**

- **Каналы (A0.6) выветрились за 3 недели.** «Вообще ничего не помню»: забыл семантику `<-`
  (send/receive), путал буферизованный/небуферизованный канал, не помнил `close`. Переактивировали
  с нуля через разговор. Урок (снова): фундамент выветривается — A0.6 нужен blank-slate ретест
  при закрытии блока.
- **Рассинхрон отправки/чтения → deadlock.** Посадил отправку `results <- ...` **внутрь**
  `if isOpen` → на закрытом порту воркер молчит, а сборщик ждёт `len(p.Ports)` результатов →
  зависание навсегда (`fatal error: all goroutines asleep`). Правило: раз собираем счётным
  циклом ровно N — слать надо на КАЖДЫЙ порт, вне `if`.
- **Ложно-зелёный тест.** Старые тесты (пустой guard + один ОТКРЫТЫЙ порт) баг рассинхрона не
  ловили — на открытом порту отправка внутри `if` срабатывает. Deadlock виден только на ЗАКРЫТОМ
  порту → добавил `TestPortProbeRunClosed`. Урок: зелёный тест ≠ рабочий код, если случай не покрыт.
- **Вложенность воркеров наизнанку.** Сначала представлял `for range jobs` снаружи и `go func`
  на каждый порт внутри — это снова «горутина на порт». Правильно наоборот: `go func` × N снаружи,
  `for range jobs` внутри каждого воркера.
- **Двойной `Close` в тесте.** В `TestPortProbeRunClosed` оставил `defer ln.Close()` + явный
  `ln.Close()`. Для закрытого порта `defer` не нужен (порт закрываем сразу, не в конце) — убрал.

**Стадии 2b + 3 (сессия 2026-07-10):**

- **Думал, строки сортируются по сумме/длине байтов.** На вопрос «как отсортируются `"80"` и
  `"443"` как строки» ответил «по количеству байт ASCII». На деле строки сравниваются
  **лексикографически** — посимвольно слева направо: `'4'(52) < '8'(56)` → `"443" < "80"`. Длина
  вторична (сравнивается только если один префикс другого). Отсюда решение: сортировать порты
  ЧИСЛАМИ (`slices.Sort([]uint16)`), в строки — в самом конце.
- **Путал `slices.Sort` и `sort.Slice`.** `slices.Sort(s)` — для упорядоченных типов, БЕЗ
  предиката (сам знает `<`). `sort.Slice(s, less)` — с предикатом-функцией `less(i,j) bool`.
  Записано в [[strings-sort]]. Для DESC — `slices.Reverse` после `Sort` или `slices.SortFunc`
  с обратным `cmp`.
- **«А зачем вообще сортировать, нам же просто список открытых».** Верно, что для человека
  порядок неважен — но тест сравнивает `Output` через `reflect.DeepEqual`, а worker pool даёт
  недетерминированный порядок → тест бы моргал (то зелёный, то красный). Сортировка = чтобы
  вывод был ДЕТЕРМИНИРОВАННЫМ и тестируемым.
- **Связка `main` после написания `parsePorts` — главный затык.** Написал `parsePorts` отдельно,
  но не понимал, как соединить в ветке `ports`: пытался сунуть сырой `*string`-флаг прямо в
  `PortProbe.Ports` (ошибка компиляции `cannot use *string as []uint16`) и забыл `targets := fs.Args()`.
  Недоставало ЗВЕНА: `--ports` (сырая строка) → `parsePorts` (строка → `[]uint16` + валидация) →
  `PortProbe{Ports: ...}`. Флаг не кладётся в структуру напрямую — между ними парсер.
- **Снова наступил на порядок флагов (`flag`).** `ports 127.0.0.1 --ports 80` не работал: `flag`
  стопорится на первом позиционном (`127.0.0.1`), `--ports` не парсится → `parsePorts("")` падает.
  Правило «флаги ДО позиционных» уже было в [[stdlib-cli]] (task-09) — выветрилось. Лечение:
  задокументировал прямо в `usage` («Flags must come before the host/domain arguments»).
- **Разнобой вывода.** До унификации: язык скакал (ru/en), префикс скакал (`p.Name():`/`parsePorts():`/
  `http:`/никак), `\n` то был то нет (склейка `out of range.exit status`), точка в конце ошибки,
  `res.Error` печатался в **stdout** вместо stderr. Свёл к одному образцу (см. «Моё решение»).
- **Рефлексия пользователя:** «всё три вызывало сомнения, пока не привык к работе». Это не провал
  по конкретной теме, а недостаток НАЛЁТА — темы свежие, автоматизма нет. Норма для этого этапа;
  лечится повторением (ретест A0.6 + следующие задачи).
