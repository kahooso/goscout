# Task-13: outpost O1 — run возвращает error, main владеет кодами выхода

Работа шла в `Desktop/outpost` (публичный репо), запись — здесь.
Пункт O1 из плана до тега v0.1.

## Задание

Незаконченный рефакторинг из прошлой сессии: `runProbe` переводился на `io.Writer`,
работа брошена на середине. Задача — довести до конца.

**Что было сломано.** Вопреки записи в roadmap, сборка была **зелёная** (`build`, `vet`,
`test` — все ok). Сломано было поведение: `errConv` возвращал `0` всегда, поэтому
`outpost bogus` завершался с кодом 0 вместо 2. Компилятор промолчал, потому что
неиспользуемый **параметр** (`args`) ошибкой не является — в отличие от неиспользуемой
локальной переменной. Мёртвый параметр в Go ловится только линтером (`unparam`, `revive`).

**Архитектурная развилка (TODO(human)):** `run` возвращал `error`, но внутри было семь
`os.Exit`. Функцию нельзя вызвать из теста (убьёт тестовый процесс), `defer f.Close()`
не выполняется. Право выходить из процесса — только у `main`.

## Моё решение

**Выбор моста «ошибка → код выхода».** Три варианта: sentinel + `errors.Is`, свой тип +
`errors.As`, либо `run` возвращает `int`. Выбрал свой тип — «чище и в дальнейшем
понадобится», плюс явное решение сохранять `%w`-цепочку.

```go
type exitError struct {
	code int
	err  error
}

func (e *exitError) Error() string { return e.err.Error() }
func (e *exitError) Unwrap() error { return e.err }

const (
	exitOK      = 0
	exitFailure = 1
	exitUsage   = 2
)

func errConv(err error) int {
	if err == nil {
		return exitOK
	}
	var ee *exitError
	if errors.As(err, &ee) {
		return ee.code
	}
	return exitFailure
}
```

Образец — `fs.PathError` из stdlib (`$GOROOT/src/io/fs/fs.go:251`): поля + `Error()` +
`Unwrap()`, pointer receiver, возвращается как `&PathError{...}`.

**Sentinel не заводили — осознанно.** Критерий: sentinel нужен, если кто-то будет
ветвиться по этой конкретной причине через `errors.Is`. Все семь причин ведут в одно
место (напечатать в stderr и выйти), ветвить нечего → `errors.New` / `fmt.Errorf` на месте.
Формулировка, к которой пришёл сам: «зачем ветвить ошибки, если мы и так по сути
на верхнем слое main».

**Итоговая раскладка ответственности:**

| Уровень | Что знает | Что делает |
|---|---|---|
| `parsePorts`, `readTargets` | конкретное значение | возвращает голую ошибку со смыслом |
| `runProbe`, `runHTTP` | что целей/URL нет | возвращает голую ошибку, **без** префикса команды |
| `run` | какая команда выполнялась | оборачивает: префикс + `%w` + код выхода |
| `main` | что это финальный вывод | печатает в stderr, зовёт `os.Exit` |

**Второй шов — `streams`.** `streams{stdout, stderr io.Writer}` протянут во все функции;
`os.Stdout` / `os.Stderr` называются по имени ровно один раз, в `main`. После правок
grep по `os.Exit` / `os.Stdout` / `os.Stderr` даёт **две строки**, обе в `main`.
Из `probe.go` и `http.go` исчез импорт `"os"` — файлы больше не знают, что живут внутри процесса.

Проверено на собранном бинаре, все восемь путей:

```
outpost                              → 2  no subcommand given
outpost bogus                        → 2  unknown subcommand: "bogus"
outpost --version                    → 0
outpost ports --ports 80             → 2  ports: no targets provided
outpost ports --ports 99999 1.2.3.4  → 2  ports: port 99999 out of range (1-65535)
outpost http                         → 2  http: no url provided
outpost dns                          → 2  dns: no targets provided
outpost dns --wordlist nope.txt      → 1  dns: cannot open wordlist: open nope.txt: ...
```

## Ошибки и трудности

**Со слов пользователя, тяжелее всего:** (1) механика `errors.As`, (2) сам факт, что
`main` абстрагирован и теперь нужно проектировать структуру ошибки — «стоит ли её
создавать». Итог сессии: «пока что всё сложненько но интересненько».

**Неверная модель `Unwrap` — держалась несколько итераций.** Формулировка была:
«`e.err = e.Error()` и мы возвращаем `e.Error` в `e.Unwrap`, где `e.Error` и так по кругу».
На деле `Unwrap()` **ничего не вызывает** — возвращает поле. Рекурсия возможна только
при вызове метода самой обёртки. Проверено прогоном: `return e.err.Error()` работает,
`return e.Error()` → `fatal error: stack overflow`, причём `go vet` на этом молчит.

**«Как `errors.As` вернёт что-то, если объект не заполнен».** Ключ: `As` не читает
переменную, а **пишет** в неё; от переменной берётся только её **тип** как образец поиска.
`nil`-указатель там нормален.

**`%v` вместо `%w` — три места.** Модель «`fmt.Errorf` просто создаёт новую ошибку с
форматированием» верна только для `%v`. Проверено прогоном: тексты побайтово одинаковые,
но `%w` даёт `*fmt.wrapError` (есть `Unwrap`), `%v` — плоский `*errors.errorString`.
`errors.Is(err, fs.ErrNotExist)`: `%w` → true, `%v` → false. Выбрал сохранять цепочку —
и на этаж ниже рвал её `%v`.

**`\n` в тексте ошибки — рецидив в той же сессии.** Сначала в трёх `fmt.Errorf`, потом
снова в `errors.New(p.Name() + ": no targets provided\n")`. Конвенция ST1005: текст ошибки —
одна строка, со строчной буквы, без точки и без `\n`; перевод строки добавляет тот, кто печатает.

**Двойной префикс команды.** `ports: ports: no targets provided` — низ добавлял `p.Name()`,
верх добавлял ещё раз. Симптом размытой ответственности: каждый уровень добавляет **свой**
контекст. Проверка при написании ошибки: «знает ли эта функция то, что пишет, из своих
аргументов?»

**При смене подхода новое добавлено, старое не удалено.** Usage печатался дважды: строка
`Fprintln(s.stderr, usage)` осталась после того, как usage переехал внутрь текста ошибки.
Компилятор такое не ловит никогда — обе строки корректны по отдельности.

**Табы внутри raw string literal.** Автоотступ редактора попал в константу `usage`, справка
печаталась с отступами. `gofmt` содержимое строк не трогает вообще — не ловится ничем,
кроме глаз. Заодно потерялся финальный `\n` перед закрывающим бэктиком.

**Регресс кода выхода при обёртке.** Все три вызова `runProbe` / `runHTTP` обернул в
`exitFailure`, хотя «не указал цели» — ошибка пользователя (`exitUsage`). Было 2, стало 1.

**Git: три коммита по файлам, средний не компилировался.** Смена сигнатуры `runHTTP` и
правка её вызова в `main.go` попали в разные коммиты. Проверено сборкой каждого коммита
в отдельном worktree: `387c23e` → `not enough arguments in call to runHTTP`. Плюс сообщения
выпали из стандарта (без `type(scope):`, точки в конце, опечатка `insted`).
Схлопнуто в один коммит через `git reset --soft` + `--force-with-lease`.

## Что бы сделал иначе

- Держать в голове таблицу «уровень → какой контекст он добавляет». Двойной префикс и
  регресс кода выхода — оба из-за того, что при обёртке не сверился с этой таблицей.
- При смене подхода сначала удалять старое, потом добавлять новое.
- Единица коммита — не файл, а изменение, которое компилируется и проходит тесты.
  Смена сигнатуры и правка всех вызовов физически неразделимы.

## Ключевые пакеты и паттерны

- Свой тип ошибки с полезной нагрузкой + `errors.As` — образец `fs.PathError`,
  `os/exec.ExitError` (`ExitCode() int`). Разбор — [[errors]].
- `%w` vs `%v` vs `errors.New` — три инструмента, три роли. Разбор — [[errors]].
- Functional core / imperative shell: `run` не знает про процесс, `main` — тонкая оболочка
  из четырёх строк без единого `if` по бизнес-логике. Разбор — [[stdlib-cli]].
- Коды выхода 0/1/2 как API программы для скриптов. Разбор — [[stdlib-cli]].
