# Скилл: give-task

**Это дефолтный скилл сессии.** Запускается на широкий набор формулировок —
пользователь не должен помнить точную фразу.

Триггеры (любая из):
- «у меня есть N часов / минут»
- «дай задание» / «дай задачу»
- «поехали» / «погнали» / «начнём»
- «что дальше» / «что делаем»
- любой неструктурированный «готов работать» / «давай»
- любое сообщение в начале сессии **после** подтверждения контекста, если оно
  не подходит под другой явный скилл (`debug`, `explain-code`, `code-review`)

Если непонятно — лучше **запустить give-task**, чем спросить «что хочешь».

**Развилка по типу задания** — определи в начале:
- Если в запросе есть «алго», «алгоритм», «LeetCode», «задачку», «размяться»,
  «потренироваться на базе» → скилл `leetcode`.
- Иначе → стандартный путь по теме из `roadmap/00-roadmap.md`.
Пользователь не знает что хочет — он хочет учиться по плану.

---

## Алгоритм

### 0. Проверь счётчик мок-собеса

Прочитай `knowledge-base/roadmap/00-roadmap.md` → счётчик задач с последнего мок-собеса.
Если счётчик **≥ 8** — предложить мок-собес вместо задания:
"Ты выполнил 8 задач с последнего мок-собеса. Хочешь сначала проверить знания?"
Если пользователь согласен → используй скилл `mock-interview`.
Если нет → продолжай выдавать задание.

### 1. Прочитай стратегию и спроси про уверенность

Прочитай `knowledge-base/roadmap/00-roadmap.md`.
Там написано: текущий блок, последний task, следующая тема, пакеты, место для кода.
Пройденное — `knowledge-base/roadmap/archive.md` («Что освоено»), чтобы не предлагать дважды.

**Перед выдачей задания прочитать `.claude/CODESTYLE.md`** — конвенции применяются
с первой строки кода, а не приводятся к ним потом на ревью.

**Если активного блока нет или блок описан в стратегии только прозой** — задание выдавать
не из чего. Переключись на `skills/plan-block/skill.md`: сначала карта заданий, потом выдача.
Не придумывать задание в обход плана — так появляются одиночные задачи без связи с блоком.

**После того как нашёл следующую тему — спроси:**
"Перед тем как дать новую тему: насколько уверенно себя чувствуешь по предыдущей —
{последняя тема}? Если есть пробелы — дам задачу-закрепление по ней, а не двинемся дальше."

Подожди ответ. Если пользователь говорит "не до конца", "слабо", "путаюсь" —
дай задачу-закрепление (см. в стратегии примеры типа `A0.2-bis`).
Если уверен — переходи к следующей теме по плану.

### 2. Определи масштаб по времени

| Время | Тип задачи |
|-------|------------|
| < 30 мин | Концептуальная задача или чтение с вопросом. Без написания кода. |
| 30–60 мин | Задача на один конкретный пакет или паттерн. |
| 1–2 часа | Три фазы подготовки + мини-утилита. |
| 2+ часов | Три фазы подготовки + полный цикл: код → тесты → запуск → ревью → vault. |

Учти реальный темп пользователя: 2–6 часов в неделю при сессии/экзаменах.
Не пытайся уместить большую тему в короткое окно.

### 2.5. Фаза 0 — проверка доменного фундамента (для предметных тем)

**Когда:** тема опирается не только на Go, но и на доменное знание — **сети** (TCP/IP,
порты, протоколы), HTTP, TLS, крипта, ОС. Для чисто Go-тем (слайсы, указатели, каналы)
этот шаг пропускается — там фундамент = сам Go, его покрывает фаза 1.

**Зачем:** пользователь окончил колледж «Программист» — доменную базу когда-то знал, но
**многое забыл** (как забыл и Go-базу, которую сейчас наверстал). Если нырнуть в Go-пакет
(`net`) поверх забытого фундамента (что такое порт, handshake) — провалимся на два уровня
ниже задачи в середине сессии. Лучше поймать это **на старте** и заложить время.

**Как:** до фазы 1 задать 1–2 вопроса на предметный фундамент темы. Примеры:
- сети → «чем порт отличается от IP? что такое TCP-соединение?»
- HTTP → «что такое метод/заголовок/статус-код? что значит stateless?»
- TLS → «зачем шифрование канала, что такое сертификат?»

Провалился → **сначала домен с нуля**, Go-пакет потом (возможно в следующую сессию).
Это **не «отставание от плана»** — доменная база засчитывается как прогресс по теме
(пример: A0.9, сессия 2026-06-18 — вся ушла на TCP/IP-фундамент, и это правильно).
Записывать в `topics/networks/` (или соответствующую папку), не только в `topics/go/`.

### 3. Три обязательных фазы перед заданием

**Всегда** проводить эти три фазы до выдачи кода. Без них задание выдавать нельзя.
Исключение: пользователь явно говорит "я знаю тему, давай сразу задание".

> **«Стоп, я не понимаю фундамент» — правильный ход, не сбой сессии.** Если пользователь
> на любой фазе тормозит («нет смысла читать дальше, я тут не шарю») — это **верное**
> поведение по `feedback_think_independently`, а не провал плана. Развернуться на фундамент,
> не тащить дальше по конспекту. Лучший результат сессии 2026-06-18 вышел именно так:
> пользователь сам остановил на фазе 1 — разобрали базу сетей, это ценнее «прошли конспект».

#### Фаза 1 — Разбор концепции (15–25 мин) — ГЛАВНАЯ ФАЗА

Объяснить как устроена концепция или структура данных изнутри.
Пользователь хочет **больше теории, больше базы**, не выдавать задание сухо.

- Что за ней стоит в памяти: где живут данные, что хранит переменная
- **Аналогии с C/C++ — НЕ использовать** (CLAUDE.md → «Язык, тон, форма»,
  memory `feedback_teaching_style`). Только если пользователь сам попросит.
- Примеры: слайс → заголовок (указатель + len + cap), ссылающийся на массив в куче;
  копия слайса делит с оригиналом один массив — вот откуда «изменил копию, изменился оригинал»
- Примеры: map → hash table, переменная хранит указатель на внутреннюю структуру
- Разобрать нулевые значения: что будет если просто объявить без make/инициализации
- Разобрать **варианты типа** — `[]T` vs `[]*T` vs `*[]T` vs `[N]T` — с памятью каждого
- Подводные камни: что ломается, что молча работает не так

После разбора **спросить**: "Что было неочевидным или непонятным?"
Если в ответе путаница — задержаться на этом моменте, разобрать ещё раз.

#### Фаза 2 — Экскурсия по пакету (10–15 мин)

Показать ключевые функции пакета который будет использоваться в задании.
- Не весь пакет — только то что нужно для конкретного задания
- Для каждой функции: сигнатура + одна строка что делает + минимальный пример
- Если пакет stdlib — открыть `pkg.go.dev/<пакет>` и сослаться оттуда
  (защита от того что Claude выдумает несуществующую функцию)
- После показа спросить: "Всё понятно? Есть вопросы по этим функциям?"
- Подождать ответа перед переходом к фазе 3

#### Фаза 3 — Контрольные вопросы (5–10 мин)

3–5 вопросов по концепции и пакету перед написанием кода.
- Задавать **по одному**, ждать ответа на каждый
- Если ответ неверный — объяснить и задать похожий вопрос повторно
- Если ответ верный — коротко подтвердить, следующий вопрос
- Только после всех правильных ответов → переходить к заданию

### 3.5. Калибровка сложности задания

**Правило:** размер задачи = текущий уровень пользователя + **одна** новая концепция.

- Одна новая концепция за задачу, не две и не три.
- Если задача требует комбинации новой темы с темой которая «сдана с пометкой не сложилось» —
  сначала закрепление слабой темы, потом новая.
- Если задача длиннее 2 часов **только** из-за объёма (не из-за сложности) — разбить на две.

**Признаки перегруза** (немедленно резать задачу):
- Требует одновременно: новой темы + незнакомого пакета stdlib + новой структуры данных
- Содержит элементы которые ещё не разбирались (например, A0.6 задача упоминает интерфейсы)
- Пользователь должен «догадаться» о чём-то что в фазах 1-2 не звучало

**Ступенчатая разбивка при перегрузе (урок 2026-07-04, A0.9).** Если задача складывает НОВУЮ
concurrency-концепцию (worker pool) поверх нового пакета (`net`) + CLI — не давать всё разом.
Ступени:
1. рабочая **последовательная** версия (обычный `for`, без горутин) + тест — доказать, что логика
   и пакет освоены;
2. превратить цикл в concurrency (worker pool);
3. обвязка (CLI/флаги/парсинг).
Пользователь на A0.9 сказал «я всё забыл, вообще ничего не понимаю», когда держал в голове
интерфейс + `net` + worker pool + CLI сразу; разгрузка до «сначала последовательно» разблокировала.
Правило «одна новая концепция» — за **ступень**, не за «задачу».

**Что НЕ делать:**
- Не «накручивать амбициозности» ради красоты задания.
- Не давать «два варианта на выбор» (вариант A простой, B сложный) — пользователь возьмёт B и сломается. Один чёткий уровень.

### 4. Сформулируй задание

Конкретно:
- Что написать (название, что принимает, что выводит).
- Какие пакеты/паттерны использовать — брать из "Следующая задача" в стратегии.
- На каком механизме тренироваться (сеть, HTTP, параллельность, безопасность).
- Где сохранить код: всегда `sections/<домен>/<имя>/main.go` (не `go/tools/...` — старый путь).
- **Тесты обязательны:** минимум 1–2 table-driven теста в `<имя>_test.go`.
  Если это первая задача с тестами — провести мини-экскурсию по `testing`:
  `t.Run`, `t.Errorf`, паттерн таблицы `[]struct{ name, in, want }`.
- Что создать в vault (`knowledge-base/tasks/task-NN.md` из шаблона).

**Домен сейчас: Go фундамент (Блок A0), затем Go + сети (под сем 4 универа).**
Не предлагать задачи по C, Rust, ручному пентесту или другим темам без явного запроса.
Ритм — вектор ведёт, универ синхронизирует (см. `learning-strategy.md` → «Главный вектор»).

### 5. Создай файл задания из шаблона

Копировать `.claude/templates/task-template.md` в `knowledge-base/tasks/task-NN.md`.
Заполнить раздел "Задание" — остальное заполнит `vault-write` по итогам.

### 6. Объясни соглашение по вопросам в коде

При выдаче задания напомнить пользователю:
"Если во время написания кода возникнет вопрос — пиши `// ? вопрос` прямо в коде.
Я отвечу на все `// ?` в ходе ревью."

### 7. Дай чеклист консольных команд (ОБЯЗАТЕЛЬНО при каждой выдаче)

Пользователь сознательно тренирует tooling руками (не кнопки VSCode). **При каждой
выдаче задания** дать блок «Проверь себя в консоли» — команды для самопроверки до
ревью. Подбирать под задачу:

Пути подставлять по месту работы: продукт — `./cmd/outpost` в репозитории outpost,
учебные артефакты — `./sections/<домен>/<имя>` здесь.

```
# по ходу написания — быстрая проверка работает ли:
go run ./sections/<домен>/<пакет> <подкоманда> <аргументы>

# перед тем как сказать «проверь» — прогнать ВСЕ:
gofmt -l ./sections/<домен>/<пакет>/        # форматирование (пусто = ок)
go vet ./sections/<домен>/<пакет>/          # статический анализ
go build ./sections/<домен>/<пакет>/        # компилируется
go test -race ./sections/<домен>/<пакет>/   # тесты + детектор гонок (если есть тесты)
```

- Объяснять, что КАЖДАЯ команда проверяет (одна строка), не просто список.
- Если в задаче нет тестов на этом шаге — `go test` пометить «после написания тестов».
- Полный справочник команд — `knowledge-base/topics/go/go-tooling.md` (ссылаться на него).
- Цель: пользователь сам гоняет ритуал и приходит на ревью с уже зелёными инструментами.

## Чего не делать

- Не давать задание без чтения стратегии — иначе задания будут хаотичными.
- Не давать задание которое уже выполнено (проверить "Освоенные темы").
- Не пропускать три фазы подготовки — пользователь явно сказал что без теории задания не работают.
- Не сокращать фазу 1 — это та фаза где пользователь больше всего просит подробностей.
- Не давать две темы сразу — одна задача, один навык.
- Не придумывать задачи "из головы" — только по стратегии.
- Не переспрашивать уровень Go — он зафиксирован в memory `user_go_level.md`.
- Не двигаться к следующей теме если пользователь не уверен в предыдущей —
  сначала закрепление (см. шаг 1).
- Не выдумывать функции stdlib — открыть `pkg.go.dev` если не уверен.
