# Скилл: refactor

Управляемый рефакторинг **инструкций и базы знаний** проекта (`.claude/` и
`knowledge-base/` + memory). Цель — менять структуру так, чтобы контекст оставался
связным: без висячих ссылок, без дублирования, без раздувания часто читаемых файлов.

**Не путать с рефакторингом Go-кода** (`cmd/`) — этот скилл про документы-инструкции
и vault, не про `.go`-файлы. Рефакторинг кода идёт через `code-review`.

**Граница с `session-debrief`** (важно, чтобы не дублировать):
- `session-debrief` = меняет **содержимое** по уже существующим местам (обновить позицию
  в стратегии, добавить строку в roadmap, запись в topics). Рутина в конце сессии.
- `refactor` = меняет **саму структуру файлов** (перенести, переименовать, разбить
  раздутый файл, свести дубли, завести новую папку). Редко, по явному `/refactor`.
- Если правка — «дописать в существующий раздел» → это debrief, не refactor.

---

## Триггеры

- `/refactor` — прямой вызов пользователем. Ссылок из CLAUDE.md на исполнение нет
  (вызывается вручную, но скилл значится в реестре, чтобы Claude о нём знал).

роль ей соответствует, — и **только туда**. Полная файловая структура проекта —
в `.claude/CLAUDE.md` → «Структура проекта» (здесь — только роли, без дублирования дерева).

## Алгоритм

### 1. Выясни идею

Один вопрос: что хочется изменить / добавить / перенести. Не предполагать — получить
замысел словами. Ждать ответа.

### 2. Уточни целевую структуру

Уточняющие вопросы (по одному), пока структура не однозначна: какие файлы затронуты,
что куда переезжает, как называется новое, какова его роль по карте выше. Расплывчатость
здесь = висячие ссылки и дубли на выходе. **Ждать подтверждения структуры перед правками.**

### 3. Выполни по жёстким правилам (инварианты — нарушение = ошибка, не выбор)

**A. Никаких висячих ссылок.**
- Любой перенос/переименование/удаление файла или раздела → обновить ВСЕ ссылки на него.
- После правок — Grep по старому пути/имени/якорю по всему репо. Ожидать 0 совпадений
  (кроме намеренных упоминаний по имени). Привести вывод проверки в отчёте.
- Помнить про два вида ссылок: wikilinks `[[name]]` резолвятся по имени (папка не важна);
  markdown `[текст](путь)` с относительным путём ломается при смене глубины — пересчитать `../`.

**B. Один модуль → один родитель-владелец.**
- Новый скилл → строка в реестре CLAUDE.md. Новый topic → строка в `_index.md`.
  Новый memory-файл → строка в `MEMORY.md`. Новая задача → строка в `00-roadmap.md`.
- В родителе указать: путь + одна строка «зачем и когда ссылаться». Без неё модуль
  невидим для LLM.
- Не прописывать один модуль в двух родителях.

**C. Структурированность и объём.**
- Формулировки конкретные, проверяемые. Никаких «по необходимости», «и т.д.» где нужно правило.
- В часто читаемые файлы — только то, что нужно часто. Редкое (история, детальные дампы) →
  в дочерний файл по ссылке.
- Сигнал к выносу: часто читаемый файл теряет сканируемость (надо скроллить ради одной
  мысли). Тогда остановиться, предложить структуру, дождаться подтверждения — не раздувать молча.

**D. Никакого дублирования.**
- Одно правило живёт в одном месте. Нужно в другом файле → ссылка, не копия.
- Особо опасно дублирование в разных формулировках — копии расходятся при правке.
  Нашёл два изложения одного правила → свести к одному, во втором оставить ссылку.
- Сверяться с картой ролей: инструкция тянет в файл с другой ролью → ей там не место.

### 4. Проверь и отчитайся

- Прогон проверки A (Grep старого → 0) с выводом.
- Подтвердить: каждый новый файл имеет ровно одного родителя; роли не пересеклись;
  часто читаемые файлы не раздулись.
- Кратко: что переехало, какие ссылки обновлены, где остались намеренные упоминания по имени.

## Чего не делать

- Не начинать правки до согласованной на шаге 2 структуры.
- Не переносить контент «на глаз» — пересчитывать относительные пути markdown-ссылок.
- Не оставлять «починю позже» — висячая ссылка сейчас = тихо сломанный контекст потом.
- Не лезть в `.go`-код — это `code-review`, не refactor.
- Не дублировать `session-debrief`: «дописать в раздел» — это debrief, refactor только
  при изменении самой структуры файлов.
