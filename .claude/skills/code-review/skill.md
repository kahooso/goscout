# Скилл: code-review

Используется когда пользователь показывает код или явно просит ревью.

---

## Полный цикл урока

```
give-task → [Фазы 1-2-3] → задание выдано
     ↓
пользователь пишет код, вопросы — через // ? в комментариях
     ↓
code-review (этот скилл)
     ↓
       ┌──────────────────┐
       │ код правильный?  │
       └──────────────────┘
          да ↓        нет ↓
    [Ветка A]      [Ветка B]
```

---

## Алгоритм

### Шаг 0 — Прогон инструментов

Перед чтением кода прогнать:

```bash
gofmt -l cmd/<имя>/    # выводит файлы которые отформатированы неправильно
go vet ./...           # ловит подозрительные конструкции
go test ./cmd/<имя>/   # запустить тесты пользователя
```

Любая находка — сразу в ревью отдельным разделом "Инструменты". Не шум:
если `gofmt -l` пустой и `go vet` молчит — упомянуть одной строкой "vet/fmt чисто".

### Шаг 1 — Прочитай код целиком

Не комментируй первую строку не видя последней.
Обязательно найти все `// ?` комментарии — это вопросы пользователя, они идут в ревью.
Проверь `_test.go` рядом — есть ли тесты, покрывают ли логику.

### Шаг 2 — Проведи ревью в чате

Структура — всегда одна:

**Что хорошо**
Конкретно — с номерами строк. Минимум 1–2 пункта.
Называй только реально хорошие решения, не натягивай.

**Что неправильно / опасно**
Баги, goroutine утечки, непроверенные ошибки, небезопасные операции, security уязвимости.
Для каждого: строка → проблема → почему опасно → как исправить.

**Что можно улучшить**
Читаемость, Go идиомы, производительность.
Приоритет: сначала корректность и безопасность, потом стиль.

**Ответы на `// ?` вопросы**
Разобрать каждый вопрос. Объяснять через аналогии с C/C++ — пользователь знает оба языка хорошо.

**Итог одной строкой**
Например: "Код рабочий, но непроверенная ошибка в строке 23 может привести к панике."

### Шаг 3 — Ветка A (код правильный или есть только мелкие замечания)

1. Ответить на все `// ?` вопросы прямо в коде: заменить `// ? вопрос` на `// A: ответ`
2. Правильные решения — добавить `// объяснение почему так` рядом с кодом (коротко)
3. Мелкие замечания — пометить `// УЛУЧШЕНИЕ: ...`
4. Дождаться подтверждения что всё понятно
5. Вызвать скилл `vault-write`:
   - Обновить `knowledge-base/tasks/task-NN.md` (все разделы кроме "Задание")
   - Если всплыла концепция которой нет в `topics/` — создать файл

### Шаг 4 — Ветка B (код с ошибками)

1. Ответить на все `// ?` вопросы прямо в коде — **всегда, даже если код неправильный**
2. Пометить каждую ошибку в коде двумя строками:
   ```go
   x = x + 1  // ОШИБКА: переменная объявлена в другом scope
               // ПОЧЕМУ: := создаёт новую переменную, а не изменяет внешнюю
   ```
3. **Не архивировать** — ждать исправления
4. Написать пользователю: "Вопросы разобраны, ошибки помечены в коде. Разберись с каждой — потом напиши 'проверь'."
5. Пользователь говорит "понял" / "проверь" → повторить шаги 1–2
6. Только после правильного кода → `vault-write`

## Соглашение по комментариям в коде

| Метка | Кто ставит | Что значит |
|-------|------------|------------|
| `// ? вопрос` | Пользователь | Вопрос во время написания кода |
| `// A: ответ` | Claude | Ответ на вопрос (после ревью) |
| `// ОШИБКА: ...` | Claude | Логическая или семантическая ошибка |
| `// ПОЧЕМУ: ...` | Claude | Объяснение почему это ошибка |
| `// УЛУЧШЕНИЕ: ...` | Claude | Код рабочий, но можно лучше |
| `// ЛИШНЕЕ: ...` | Claude | Код который не нужен |

## Go-специфичные вещи которые всегда проверять

- **Тесты**: есть ли `_test.go`? Покрывают логику или только happy path?
  Используется ли `t.Run` для table-driven? Падают ли с понятным сообщением?
- **Ошибки**: все `err` проверены? Нет `_ =` без причины?
- **Goroutine leaks**: все запущенные горутины завершатся? Каналы закрыты?
- **HTTP**: `resp.Body.Close()` после каждого запроса?
- **Context**: используется `context` с таймаутом для сетевых вызовов?
- **SQL**: запросы через `?` плейсхолдеры, не строковая конкатенация?
- **Secrets**: нет ли захардкоженных токенов, паролей, ключей?
- **TLS**: не выключена ли верификация сертификата (`InsecureSkipVerify: true`)?
- **Перенос C-привычек**: лишние nil-checks в бизнес-методах, `var x []T = []T{...}`
  вместо `:=`, явная инициализация нулевыми значениями (`IsDone: false`),
  `make(map, 0)`, `var s []T` без pre-allocate когда размер известен.
  Это типичный паттерн для пользователя — отмечать каждый раз пока не уйдёт.

---

## Уровень строгости

По корректности и безопасности — честно, без смягчений.
По стилю — указывай, но не придирайся к мелочам.

## Чего не делать

- Не переписывать код за пользователя на шаге 2 — объяснить что не так и почему.
- Не пропускать `// ?` вопросы — они всегда отвечаются, даже если код неправильный.
- Не архивировать в vault пока код не прошёл ревью чисто.
- Не говорить "хороший код" если есть баги или security проблемы.
