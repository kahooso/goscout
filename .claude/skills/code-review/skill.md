# Скилл: code-review

Используется когда пользователь показывает код или явно просит ревью.

---

## Полный цикл

```
give-task → [3 фазы] → задание выдано
        ↓
пользователь пишет код; вопросы — // ?
        ↓
code-review (этот скилл)
        ↓
   ┌────────────────┐
   │ код правильный?│
   └────────────────┘
     да ↓     нет ↓
  Ветка A   Ветка B
```

---

## Алгоритм

### Шаг 0 — Прогон инструментов

```bash
gofmt -l sections/<домен>/<имя>/     # выводит файлы с неправильным форматированием
go vet ./...            # статический анализ — подозрительные конструкции
go build ./sections/<домен>/<имя>/   # компилируется
go test -race ./sections/<домен>/<имя>/   # тесты + детектор гонок
```

Любая находка → раздел «Инструменты» в ревью. Если всё чисто — одной строкой «vet/fmt/build/race чисто».

**Пользователь тренирует tooling руками.** Прежде чем самому прогнать инструменты —
дать пользователю эти команды списком, чтобы он прогнал сам (привычка к консоли, не
кнопки VSCode). Если он уже прогнал и приложил вывод — не дублировать, просто свериться.
Справочник команд — `knowledge-base/topics/go/go-tooling.md`.

### Шаг 1 — Прочитать код целиком

Не комментировать первую строку не видя последней.
Найти все `// ?` — они **всегда** разбираются в ревью.
Проверить `_test.go`: есть ли? Покрывают логику или только happy path?
**Минимум 3 кейса:** happy + граничный + злой/паника-кейс.

### Шаг 2 — Ревью в чате

Структура всегда одна:

**Что хорошо** — конкретно, с номерами строк. 1–2 пункта минимум. Не натягивать.

**Что неправильно / опасно** — баги, goroutine утечки, непроверенные ошибки, паники, security.
Формат: строка → проблема → почему опасно → как исправить.

**Что можно улучшить** — читаемость, идиомы, производительность.
Приоритет: сначала корректность и безопасность, потом стиль.

**Стиль — отдельной секцией.** Сверить с `.claude/CODESTYLE.md` и вынести расхождения
списком, НЕ смешивая с багами. Стиль обсуждению не подлежит: он уже решён, задача ревью —
привести код к эталону, а не спорить о нём.

**Ответы на `// ?` вопросы** — на языке Go, БЕЗ аналогий с C/C++ (CLAUDE.md → «Язык, тон, форма», memory `feedback_teaching_style`).

**Итог одной строкой** — например: «Рабочий, но непроверенный `kv[1]` в строке 46 паника на пустом вводе».

### Шаг 3 — Ветка A (код правильный или мелкие замечания)

1. Ответить на все `// ?` прямо в коде: заменить `// ? вопрос` на `// A: ответ`.
2. Правильные решения — короткий `// объяснение почему так` (1–2 строки, не лекция).
3. Мелкие замечания — пометить `// УЛУЧШЕНИЕ: ...`.
4. **Длинные объяснения (>3 строк) — НЕ оставлять в коде.** Перенести в `topics/go/<тема>.md`
   в раздел «Личный опыт» или новый подраздел. В коде — ссылка:
   ```go
   // см. topics/go/pointers.md#value-vs-pointer-receiver
   ```
5. Дождаться подтверждения «понятно».
6. Вызвать `vault-write`:
   - Обновить task-файл рядом с кодом (`sections/<домен>/<имя>/task-*.md`):
     разделы «Моё решение», «Ошибки и трудности», «Что бы сделал иначе»
   - Перенести длинные `// A:` в `topics/go/<тема>.md` (раздел «Личный опыт»)
   - Если всплыла новая концепция — новый файл в `topics/`

### Шаг 4 — Ветка B (есть ошибки)

1. Ответить на все `// ?` прямо в коде — **всегда**, даже если код неправильный.
2. Пометить каждую ошибку двумя строками:
   ```go
   x = x + 1  // ОШИБКА: переменная объявлена в другом scope
              // ПОЧЕМУ: := создаёт новую, а не изменяет внешнюю
   ```
3. **Не архивировать** — ждать исправления.
4. Сказать: «Вопросы разобраны, ошибки помечены. Разберись с каждой — потом напиши `проверь`».
5. После исправления → повторить шаги 1–2.
6. Только после правильного кода → ветка A.

## Природа ошибки — определить ДО того, как писать пункт

Объём разбора задаётся **природой** ошибки, а не её критичностью. Одинаково подробный
разбор опечатки и архитектурного промаха — то, из-за чего task-12 растянулся на пять
итераций и закончился словами «устал, ничего не понятно».

| Природа | Как разбирать |
|---------|---------------|
| **Опечатка / невнимательность** (`&` вместо `&&`, приоритет операторов, не то имя переменной) | Сказать прямо, 1–2 строки. Без наводящих вопросов — их нечего наводить. |
| **Механический промах рефакторинга** (сигнатура ↔ вызов, индекс, забытый параметр) | Прямо + назвать класс ошибки, чтобы узнавался в следующий раз. |
| **Незнание факта или контракта** (что возвращает функция, когда канал закрыт) | Объяснить абзацем, дать опору: пакет, конспект в `topics/`, кусок stdlib. |
| **Логическая / архитектурная** (не та точка проверки, deadlock, дырявая абстракция) | Полный разбор в три слоя: что происходит → почему это плохо → как перестроить. Плюс вопрос на понимание. **Сократический режим только здесь.** |

**Рецидив помечать только на критичных багах.** Мелочь, которую пользователь сознательно
пропустил, повторно не поднимать — это шум, из-за которого теряются важные пункты.

## Итеративные сессии — один файл несколько раз подряд

Второй и последующий заход по тому же коду:

- **Не начинать заново.** Проверять только то, что менялось, плюс последствия правок.
- **Считать итерации вслух:** «итерация 3 по `PortProbe.Run`». Пользователь должен видеть,
  сколько кругов уже сделано.
- **Три итерации подряд по одной функции — сигнал**, что разбор идёт не туда. Остановиться
  и спросить прямо: разбираем дальше или дописываем вместе и идём к следующей теме.
- **Признак усталости** («не понял», «давай ты», «устал») — не повод продолжать в том же
  темпе. Сменить режим: короткое прямое объяснение вместо вопросов.

## Соглашение по комментариям

| Метка | Кто ставит | Что значит |
|-------|------------|------------|
| `// ? вопрос` | Пользователь | Вопрос во время написания |
| `// A: ответ` | Claude | Короткий ответ (1–3 строки) |
| `// ОШИБКА: ...` | Claude | Логическая/семантическая ошибка |
| `// ПОЧЕМУ: ...` | Claude | Объяснение почему это ошибка |
| `// УЛУЧШЕНИЕ: ...` | Claude | Код рабочий, можно лучше |
| `// ЛИШНЕЕ: ...` | Claude | Код не нужен (и **удалить**, не просто пометить) |
| `// см. topics/...` | Claude | Длинное объяснение перенесено в vault |

**Главное правило:** код = код, vault = vault. В коде только то, что объясняет
именно этот фрагмент в 1–3 строках. Всё длинное — в `topics/`.

## Что всегда проверять (Go specific)

- **Тесты**: есть `_test.go`? Минимум 3 кейса (happy + граничный + злой)? `t.Run` для table-driven? Падают с понятным сообщением?
- **Concurrency**: запускался ли `go test -race`? Все горутины завершатся? Каналы закрыты?
- **Ошибки**: все `err` проверены? `kv[1]` без `len(kv) == 2` — потенциальная паника.
- **HTTP**: `defer resp.Body.Close()` после каждого запроса?
- **Context**: `context.WithTimeout` для сетевых вызовов?
- **SQL**: плейсхолдеры `?`, не конкатенация строк?
- **Secrets**: нет ли захардкоженных токенов/ключей?
- **TLS**: не `InsecureSkipVerify: true` без причины?
- **C-привычки**: лишние nil-checks в бизнес-методах, `var x []T = ...` вместо `:=`,
  явная инициализация zero values (`IsDone: false`), `make(map, 0)`. Помечать каждый раз
  пока паттерн не уйдёт (см. memory `feedback_c_idioms_in_go.md`).

## Уровень строгости

- Корректность и безопасность — честно, без смягчений.
- Стиль — указывать, но не придираться к мелочам.
- «Хороший код» не говорить если есть баги или security проблемы.

## Чего не делать

- Не переписывать код за пользователя на шаге 2 — указать что и почему, исправляет он.
- Не пропускать `// ?` вопросы — всегда отвечать, даже при ошибках в коде.
- Не архивировать в vault пока ревью не прошло чисто.
- Не оставлять длинные `// A:` в коде — переносить в `topics/`.
- **При удалении** длинного учебного комментария из старого кода (чистка перед новой темой,
  ответ на «причеши код») — СНАЧАЛА Grep по `topics/<кат>/<тема>.md` на ключи этой мысли.
  Если в vault нет — добавить туда раньше, чем удалить из кода. Типовой подвох — «и так
  помню, недавно же писали» → не сверился → знание тихо потерялось.
