# Скилл: lab

Общий цикл лабы для всех предметов (схемотехника/Multisim, ОС/Pintos, ЯП/компиляторы, БЖД/стенды). Особенности предмета — в его трекере, раздел «Софт» и «Режим».

**До действия:** [`TEACHER.md`](../../TEACHER.md), профиль `lab`. Главное — §1 «разделение труда»: расчёты, код, сборку схем, выводы делает пользователь; Claude объясняет, ведёт по шагам и проверяет.

## Триггеры

«лаба», «ЛР-N», «лабораторная», «делаем отчёт», «проверь отчёт», передача из `study`.

## Папка лабы

`university/<N>-semester/<предмет>/labs/labN/`. **Перед записью — `ls`** (в EST однажды создали папку-дубль рядом с существующей). Файлы:

| Файл | Что | Кто пишет |
|---|---|---|
| `plan.md` | пункты методички, настройки, статус, «где остановились» | Claude (шаблон `university/_templates/lab-plan.md`) |
| `otchet.md` | справочная версия отчёта: структура, теория, таблицы | Claude + пользователь |
| `zashchita.md` | ответы к защите своими словами | пользователь, Claude проверяет (скилл `defense`) |
| отчёт `.docx` | сдаётся | пользователь (локально, в git не идёт) |
| `*.ms11`, `*.py`, код, графики | рабочие файлы | по ситуации |

## Алгоритм

### 1. Задание

Методичка/требования — в `gostudy-materials` (путь и страницы — в трекере предмета). Извлечь текст (`university/README.md` → «Материалы»). Разобрать: цель, пункты, что требуется в отчёте, контрольные вопросы.

### 2. План

Написать `plan.md`: пункты по порядку; для каждого — что сделать, что это значит, что должно получиться, что идёт в отчёт (📸). Теория, которая понадобится, — ссылками на `lectures/`; чего нет — пометить «разберём на пункте N». Показать план кратко, спросить «начинаем с пункта 1?».

### 3. Пункты по порядку — теория по ходу

Формат одного шага: **пункт → что сделать → что это значит → что увидишь**. Теория — ровно та, что нужна для текущего пункта, простым языком, на числах из этой лабы. Чистая теория блоками до практики на этих предметах не зашла (EST, 2026-09-10).

- Пользователь делает сам (кликает, собирает, запускает, считает) и присылает скриншоты / вывод / числа.
- Claude **сверяет по скриншоту/выводу**, а не по памяти: тип детали, положение переключателей, развёртку осциллографа, что к чему подключено. Номиналы для расчёта — с последнего скриншота пользователя.
- Расчёт: пользователь считает → Claude проверяет и указывает место ошибки, не пересчитывает за него. Если пользователь просит посчитать скриптом (много однотипных точек) — можно, но одну точку он считает руками и объясняет.
- После каждого пункта — один короткий вопрос «почему получилось так?» (не «понятно?»). Ответ — сразу заготовка для `zashchita.md`.
- Статус и «где остановились» в `plan.md` — обновлять после каждого пункта.

### 4. Отчёт

- Каркас, оформление, таблицы из данных пользователя, графики (`matplotlib` → `grafik_*.png`) — может Claude.
- **Выводы — пишет пользователь**, Claude правит по сути. Выводы и есть материал защиты.
- В отчёт идут **свои** скриншоты пользователя. Чужие отчёты — только как образец формы, не копировать: у одногруппников бывали фактические ошибки.
- **Word-файл после ручной правки пользователя — только читать.** Генератор (`sborka.py`) — только для самого первого каркаса. Дальше точечные правки — только с явного разрешения, без изменения оформления, с копией до правки. Скриншоты вставляет пользователь, Claude проверяет, что они правильные.
- Проверка готового `.docx`: текст и порядок картинок — `word/document.xml` + `word/_rels/document.xml.rels`, картинки — `word/media/`. Ловить: расхождение скриншот ↔ текст, пропущенные пункты методички, единицы, развёртку, фактические ошибки.

### 5. Закрытие

1. Вопросы по лабе в `recall.md` предмета: 4–8 штук (механизм, «что будет если», формулы) + контрольные вопросы методички.
2. Предложить сразу `defense` для `zashchita.md`, если защита скоро.
3. Трекер (`README.md` → «Лабы», «Где я сейчас», дедлайн защиты), `journal.md`.

## Предмет-специфика

Держится в трекере предмета («Софт», «Факты, которые легко забыть»). Если в трекере есть строка «Разделение труда» — она важнее алгоритма выше (пример: схемотехника — отчёт и расчёты делает Claude, теория отдельным днём). Примеры: Multisim не автоматизируется, кликает пользователь, скриншот окна — только `PrintWindow`, не `CopyFromScreen` (захватывает чужие окна); настоящий GCC — `C:\mingw64\bin\gcc.exe`, первый `gcc` в PATH — clang; Pintos — в ВМ по `ssh pintos`. **Считаешь по SPICE-модели детали — параметры только из окна Edit model детали на схеме пользователя** (в базе Multisim бывает несколько записей с одним именем; ЛР-7: взял чужую 2N2222A — расхождение 7,5 дБ, пересчёт всего отчёта). Первая сверка — одна точка Боде до сборки отчёта.

## Чего не делать

- Не считать, не писать код и выводы за пользователя без аварийного выхода (`TEACHER.md` §1).
- Не утверждать про схему/вывод без сверки со скриншотом.
- Не создавать папку лабы, не проверив `ls`.
- Не трогать `.docx` после ручной правки пользователя.
