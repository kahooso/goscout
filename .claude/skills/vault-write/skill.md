# Скилл: vault-write

Триггеры:
- прямая просьба: «добавь в vault», «запиши тему», «обнови knowledge-base»
- вызов из `session-debrief` (шаги 2–3)
- вызов из `explain-code` после объяснения новой концепции
- вызов из `code-review` (Ветка A → перенос длинных `// A:` в vault)
- вызов из `debug` после типичной ошибки

---

## Алгоритм

### 1. Задать один вопрос (если ещё не задавали в этой сессии)

> «Что было сложным, непонятным или интересным?»

Один вопрос. Ответ влияет на содержание и подробность записи.

**Исключение:** если вызов из `session-debrief` и вопрос там задан — использовать тот ответ.

### 2. Определить тип записи

| Ситуация | Куда |
|----------|------|
| Go пакет, паттерн, идиома | `knowledge-base/topics/go/<тема>.md` |
| Сетевой протокол | `knowledge-base/topics/networks/` |
| AppSec концепция | `knowledge-base/topics/security/` |
| Выполненное задание | `knowledge-base/tasks/task-NN.md` |
| Обновление существующего | найти файл → дополнить (не создавать новый) |

Перед созданием нового файла — проверить что его нет (`Glob` по имени).

## Структура `topics/` файла — НОВЫЙ формат

```markdown
# <Название концепции>

## TL;DR
Одна строка. Что это в одном предложении.

## Где разобрано подробно
- `gobyexample.com/<тема>` (если есть)
- `pkg.go.dev/<пакет>` (если stdlib)
- `effective_go.md#section` (если уместно)
- (опционально) видео Николая Тузова — название без URL

## Минимальный пример
```go
// 5–15 строк реального кода, не generic
```

## Личный опыт

### Что я понял не сразу
- Конкретные ошибки и почему я раньше думал иначе.
- Откуда привычка (C/C++/Java/Python) и где она ломается в Go.

### На чём попадался
- `task-NN`: <короткое описание ошибки и как исправил>
- если повторялось — отметить «(уже было в task-XX)»

### Подводные камни
- что молча работает не так
- что вызывает панику
- security implications если есть

## Ключевые термины (English)
- `term` — короткое пояснение / русский эквивалент
- 3–7 терминов темы: названия функций, концепций, идиом на английском.
  Это словарь для собесов и чтения доков. См. принцип English-словаря в стратегии.

## Связанные темы
[[wikilink]] [[wikilink]]
```

**Главное отличие от старого формата:** generic-теории минимум (для неё есть ссылка).
Основное содержание — личный опыт пользователя. Если опыта ещё нет —
раздел остаётся пустым с пометкой «заполнится после первой ошибки».

**English-глоссарий обязателен** для каждой новой `topics/`-записи (правило стратегии).
Старые записи не переписывать массово — добирать раздел при следующем редактировании файла.

## Структура `tasks/` файла

```markdown
---
id: task-NN
block: A0.X
topic: <название>
status: completed
date_started: YYYY-MM-DD
date_completed: YYYY-MM-DD
---

# Task-NN: <название>

## Задание
<формулировка из give-task>

## Моё решение
Реальный подход, не план из задания.

## Ошибки и трудности
Всё что было сложным — включая ответ на вопрос «что было непонятным».
Перечислять конкретные баги: какая строка → что было неправильно → как исправил.

## Что бы сделал иначе
Рефлексия.

## Ключевые пакеты и паттерны
Что использовал, зачем.

## Связанные темы
[[wikilink]] [[wikilink]]
```

## Когда переносим длинные `// A:` из кода в `topics/`

Контекст: `code-review` Ветка A пункт 4. В коде остался комментарий длиннее 3 строк.

Действия:
1. Прочитать длинный комментарий.
2. Найти в `topics/go/<тема>.md` раздел «Личный опыт → Что я понял не сразу».
3. Добавить туда новый пункт со ссылкой на task-NN.
4. В коде заменить длинный комментарий на:
   ```go
   // см. topics/go/<тема>.md#что-я-понял-не-сразу
   ```

---

## Чего не делать

- Не писать generic-теорию там где её можно заменить ссылкой.
- Не создавать новый файл если тема уже есть — сначала проверить через Glob.
- Не дублировать: tasks/ про опыт конкретной задачи, topics/ про концепцию.
- Не пропускать шаг 1 (если вопрос ещё не задавался).
- Не начинать запись с длинного введения — сразу к сути.
