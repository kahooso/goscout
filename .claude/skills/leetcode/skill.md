# Скилл: leetcode

Параллельный трек алго-задач. Две функции: **посоветовать следующую** и **оформить решённую**.

План и прогресс — `sections/leetcode/00-roadmap.md`. Это единственный источник истины
по прогрессу: отметка `[x]`, не наличие папки.

---

## Триггеры

«дай алго» / «алгоритм» / «LeetCode» / «задачку» / «размяться» / «потренироваться на базе».
Из `give-task`, когда запрос попал в ветку algo.

---

## A. Посоветовать следующую задачу

### 1. Прочитать план

`sections/leetcode/00-roadmap.md` → раздел «План». Найти **первую строку с `[ ]`**
по порядку разделов.

### 2. Проверить слабые паттерны

Раздел «Слабые паттерны» в том же файле. Если там есть паттерн, отмеченный
«с подсказкой» или «со скрипом», и он старше двух недель — предложить **его** вместо
следующей по порядку: возврат к слабому важнее движения вперёд.

### 3. Проверить, что паттерн уже проходили

Задача не должна опираться на тему, которой нет в `roadmap/archive.md` → «Что освоено».
Опирается на непройденное → взять следующую доступную, назвать причину.

### 4. Выдать СПИСОК 2–4 задач, не одну

Правило пользователя (memory `feedback_algo_practice` — источник истины):
Claude **даёт список** → пользователь выбирает сам, что и сколько решать.
На каждую строку: название, сложность, паттерн, одна фраза «зачем сейчас».
Ссылку на leetcode.com не генерировать — назвать slug, пользователь откроет сам.

### 5. Куда писать код — гибрид

- **Простые задачи** решаются прямо на leetcode.com, в репозиторий не тащим.
- **Новый паттерн или сложная** → каталог в репозитории. Заготовку заводить
  ТОЛЬКО по явному «беру» / «погнали»: скопировать `sections/leetcode/_TEMPLATE/`
  в `sections/leetcode/<slug>/`, переименовать пакет и файлы.
- **Отметку `[x]` при создании папки не ставить** — папка это хранилище, не статус.

### 6. Формат сессии (~30–60 мин)

1. Постановка: задача коротко, сигнатура, пример (1–2 мин).
2. Разговор про подход: наивное решение → его сложность → куда двигаться (5–10 мин).
   Не выдавать оптимальное решение — вести вопросами.
3. Пользователь пишет код и тесты сам (~20 мин). Вопросы в коде через `// ?`.
   Не подсказывать заранее — только если явно застрял или нажал escape hatch
   (memory `feedback_think_independently`).
4. Ревью через скилл `code-review`.
5. Оформление — часть B ниже.

---

## B. Оформить решённую задачу

**Документировать не каждую.** «Решил, всё очевидно» — только отметка `[x]`, без notes.
Полное оформление — если новый паттерн, если застрял и разбирали, если урок на ревью.

### 1. Поставить отметку

В `sections/leetcode/00-roadmap.md` заменить `[ ]` на `[x]` в строке задачи, дописать дату.

### 2. Положить решение

`sections/leetcode/<slug>/<имя>.go` + `<имя>_test.go`. Пакет = имя задачи, не `main`.
Минимум три кейса теста: обычный, граничный, злой.

### 3. Заполнить notes.md

По шаблону `_TEMPLATE/notes.md`: паттерн, идея, сложность, наивный вариант и почему хуже,
грабли Go, поле **«далась: легко / со скрипом / с подсказкой»**.

### 4. Обновить слабые паттерны

Далась «со скрипом» или «с подсказкой» → строка в раздел «Слабые паттерны»
с датой и одной фразой, что именно не сложилось.

### 5. Новый паттерн → конспект

Паттерн встретился впервые → `knowledge-base/topics/algo/<паттерн>.md` через `vault-write`,
строка в `topics/_index.md`, строка в `roadmap/journal.md` → «Algo-практика».

---

## Чего не делать

- Не выдавать алго вместо темы основного блока, если пользователь не попросил явно.
- Не превращать в марафон: это закрепление, а не цель. ~1 задача на 2–3 задания блока.
- Не ставить `[x]` при создании папки — только при записанном решении.
- Не давать решение до того, как пользователь сам попробовал подход.
- Не брать задачу на непройденном паттерне.
