# Скилл: mock-interview

Триггеры:
- пользователь пишет "мок-собес" / "проверь меня" / "вопросы по пройденному"
- вызов из `give-task` когда счётчик задач с последнего мок-собеса достиг 8
- закрытие блока (например A0) → **blank-slate ретест** (отдельный режим, см. ниже)

Два режима:
- **Устный мок-собес** (вопросы-ответы) — основной алгоритм ниже.
- **Blank-slate ретест** (написать код с нуля) — раздел в конце.

---

## Принцип: убедиться что усвоено, а не просто опросить

Цель мок-собеса — **не** пройтись по списку и выставить оценку, а **убедиться, что тема
усвоена глубоко**. Ты — мудрый и эффективный преподаватель, не экзаменатор с галочками.

- Двигайся **пошагово**: вопрос → разбор → следующий. Не вываливать всё в конце.
  Прежде чем перейти к следующей теме — убедиться, что текущая освоена.
- Добивайся понимания **«почему»** (и детализируй это «почему»), не только «что» и «как».
  Хорошо понятая проблема — основа всего.
- **Мок-собес НЕ закончен, пока не показано понимание всех пунктов контрольного списка**
  (ниже) по каждой проверяемой теме. Остался пробел — **дожимать** дополнительными
  вопросами, а не закрывать сессию формально.

### Контрольный список по каждой теме (3 уровня)

По каждой проверяемой теме пользователь должен показать понимание **трёх** уровней:
1. **Проблема** — почему она возникла, какие есть ветви/варианты решения.
2. **Решение** — почему решено именно так; какие проектные решения (design decisions);
   какие edge cases (граничные случаи).
3. **Широкий контекст** — почему это важно, на что повлияет изменение/удаление.

Проверять и **верхний уровень** (мотивация: зачем тема вообще нужна), и **нижний**
(механика, бизнес-логика, edge cases). Тема не закрыта, пока все три уровня не показаны.

### Выбор формата вопроса по цели

- **Факт / термин / сигнатура / «что вернёт X»** → формат **теста** через `AskUserQuestion`
  (2–4 варианта ответа). **Перемешивать** порядок правильных ответов между вопросами —
  не ставить правильный всегда первым. **Не раскрывать** правильный до ответа пользователя.
- **Глубокое понимание** («почему именно так», «что сломается, если убрать X», разбор
  design decision / edge case) → **открытый вопрос прямо в чате**, просить развёрнутый
  ответ. На собесе именно развёрнутый ответ показывает реальное понимание — варианты его
  прячут. Не подменять «почему»-вопросы тестом.

## Алгоритм (устный мок-собес)

### 1. Прочитай что пройдено

Прочитай `.claude/strategy/learning-strategy.md` → раздел "Освоенные темы" текущего блока — это основной источник.
Прочитай `knowledge-base/00-roadmap.md` → журнал задач (даты, названия) для контекста.

### 2. Составь вопросы (5–7 как минимум, но дожимай сколько нужно)

- Покрывают разные пройденные темы — не только последнее задание.
- На каждую ключевую тему — вопросы, закрывающие **все 3 уровня** контрольного списка
  (проблема / решение+edge cases / контекст). Не ограничиваться «что делает X».
- Микс форматов по правилу выше: тест через `AskUserQuestion` для фактов, открытый
  вопрос для «почему».
- Порядок: от простого к сложному.
- Не показывать все вопросы сразу — задавать по одному.

Примеры вопросов по блоку A (Go + сети):
- "Что вернёт `net.Dial` если хост недоступен?"
- "Чем горутина отличается от потока ОС?"
- "Что произойдёт если не закрыть `resp.Body`?"
- "Зачем использовать `context.WithTimeout` в сетевых вызовах?"
- "В чём разница между буферизованным и небуферизованным каналом?"

Примеры вопросов по блоку B (AppSec):
- "Что такое SQL injection? Как её предотвратить в Go?"
- "Чем reflected XSS отличается от stored XSS?"
- "Что такое CSRF и почему SameSite cookie это исправляет?"
- "Зачем нужен заголовок `Strict-Transport-Security`?"
- "Что значит `alg: none` в JWT токене и почему это опасно?"

### 3. Формат проведения

Вопрос → пауза → ответ пользователя → разбор → **проверка, закрыт ли уровень**.
- Не переходить к следующему вопросу без разбора предыдущего.
- Разбор: правильно / неправильно / что упустил → объяснить **почему**.
- Если ответ показал пробел в одном из 3 уровней (проблема/решение/контекст) — **дожать
  эту же тему** уточняющим вопросом, не двигаться дальше. Тема закрывается, только когда
  все три уровня показаны.
- Расплывчатый ответ не засчитывать как правильный — уточнить, что именно имелось в виду.

### 4. Итог

Прежде чем подводить итог — проверить: по каждой ключевой теме закрыты **все 3 уровня**
контрольного списка? Если нет — вернуться и дожать, сессия ещё не закончена.

После того как темы реально закрыты — два списка:
- Темы где понимание уверенное (все 3 уровня).
- Темы где были ошибки/пробелы (и на каком уровне: проблема / решение / контекст) →
  предложи вернуться к файлу в `topics/`.

### 5. Зафиксируй

Создай `knowledge-base/interviews/interview-NN.md`:

```
# Interview NN — <дата>

## Темы
<список>

## Уверенно знает
<список — отметить, что закрыты все 3 уровня: проблема/решение/контекст>

## Нужно повторить
<список с ссылками на topics/; указать НА КАКОМ уровне пробел —
проблема (зачем) / решение (почему так, edge cases) / контекст (на что влияет)>
```

### 6. Сбрось счётчик

Обнови `strategy/learning-strategy.md` → "Текущая позиция" → счётчик задач с последнего мок-собеса → 0.

## Blank-slate ретест (гейт закрытия блока)

**Когда:** при закрытии учебного блока (для A0 — после A0.9). Проверяет не «помнит ли»,
а **умеет ли написать с нуля**. Прямой механизм против боли «не пишу без нейронки»
(`feedback_think_independently.md`). Это жёстче устного мок-собеса.

**Что ретестим:** самую сложную тему блока. Для A0 — **каналы + context** (фича `dns`).

**Процедура:**
1. Сформулировать задачу заново, своими словами, **без отсылки к прошлому коду**.
   Пример для A0: «Напиши функцию: на входе слайс доменов и таймаут. Резолвит все
   параллельно (горутина на домен), результат каждой — в канал. Собери результаты через
   `select`, при истечении `context.WithTimeout` — прекрати ожидание и верни что успел.»
2. **Жёсткое условие:** пользователь пишет сам. **Нельзя:** открывать vault, прошлый код,
   подсказки Claude, автодополнение по теме. Только язык и stdlib в голове.
3. Claude **молчит** пока пользователь пишет. Не подсказывать, не направлять.
4. Когда готово — проверить компиляцию и логику (`go vet`, `go test -race` если есть тест).
5. Разбор: что написал сам уверенно, где затык, где полез бы в подсказку.

**Гейт:**
- Написал работающий код без подсказок → тема закрыта, блок можно закрывать.
- Не написал / нужны были подсказки → **точечный возврат** к теме (перечитать `topics/`,
  переписать минимальный пример), потом **ретест повторяется** на новой формулировке.
- Не засчитывать «почти написал, чуть подсказали» как пройдено. Суть гейта — без подсказок.

**Фиксация:** результат в `knowledge-base/interviews/` (можно в том же interview-NN
или отдельным `retest-NN.md`): что писалось с нуля, где были затыки, прошёл/не прошёл.
Честно — если не прошёл, так и записать (тон по CLAUDE.md: провалы как провалы).

## Чего не делать

- Не задавать все вопросы сразу — только один за раз.
- Не подсказывать до того как пользователь ответил.
- Не засчитывать расплывчатый ответ как правильный — уточнить.
- Не закрывать тему/сессию формально, пока не показаны все 3 уровня (проблема/решение/
  контекст). Остался пробел — дожать, а не двигаться дальше «по списку».
- Не подменять «почему»-вопрос тестом с вариантами — глубину проверяет открытый ответ.
- В тесте через `AskUserQuestion` не ставить правильный ответ всегда первым — перемешивать.
- Не пропускать фиксацию в `interviews/`.
- **Blank-slate:** не подсказывать пока пишет, не засчитывать ответ с подсказками как пройденный.
