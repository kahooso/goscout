# Скилл: debug

Триггеры: "не компилируется", "паника", "panic", "deadlock", "race condition", "ошибка", "не работает",
пользователь вставляет вывод `go build` / `go run` / `-race` / `dlv`.

---

## Алгоритм

### 1. Собери контекст

Если пользователь не вставил текст ошибки — попроси:
"Вставь вывод `go build` / `go run` / полный стектрейс паники."

Если код не виден — прочитай файл сам (спроси путь если неизвестен).
Не гадай по описанию — нужен реальный текст ошибки.

### 2. Классифицируй ошибку

| Тип | Признак |
|-----|---------|
| Ошибка компиляции | `go build` вывел `cannot`, `undefined`, `type mismatch`, `syntax error` |
| Panic: nil pointer | `panic: runtime error: invalid memory address or nil pointer dereference` |
| Panic: index out of range | `panic: runtime error: index out of range` |
| Deadlock | `fatal error: all goroutines are asleep - deadlock!` |
| Race condition | `WARNING: DATA RACE` (запускать с флагом `-race`) |
| Логическая ошибка | программа работает, вывод неправильный |

### 3. Дай hint — не решение

- Укажи файл и строку где проблема.
- Объясни что именно не так и почему это ошибка.
- Задай направляющий вопрос: "Что произойдёт если `resp.Body` не закрыть?"
- Подожди — пусть пользователь попробует сам.

### 4. Инструменты отладки Go

Если пользователь не знает как дебажить — объяснить:

| Инструмент | Когда |
|------------|-------|
| `go vet ./...` | статический анализ, ловит подозрительный код |
| `go run -race .` | детектирование race conditions |
| `dlv debug` | интерактивный дебаггер (breakpoint, print vars) |
| `fmt.Println` / `log.Printf` | самый простой способ — добавить принты |
| `go test -v -run TestName` | запуск одного теста с выводом |

Называть инструмент только с объяснением что он делает.

### 5. Если hint не помог

- Покажи минимальный пример где ошибка воспроизводится.
- Объясни как читать стектрейс паники — файл, строка, goroutine.
- Только если пользователь совсем застрял → показывай исправление с объяснением почему именно так.

### 6. Зафиксируй

Если ошибка типичная (не проверил err, nil pointer, горутина утекла, забыл закрыть resp.Body) —
предложи добавить в vault:
"Добавить в vault как типичную ошибку?" → используй скилл `vault-write`.

---

## Чего не делать

- Не давать исправленный код сразу — сначала hint.
- Не игнорировать предупреждения `go vet` — объяснять как ошибку.
- Не называть инструменты без объяснения что они делают.
- Не чинить несколько проблем за раз — одна ошибка → один hint.
- Не переписывать функцию целиком чтобы "починить" — только точечное указание.
